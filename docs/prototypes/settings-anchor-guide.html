首轮工具清单锚定（实验）

发给模型的每次请求都带一份「工具清单」（请求里的 tools 菜单，与项目文件夹无关）， 清单中途变化会打断前缀缓存、分散模型首轮注意力。开启锚定后，新会话第一轮只展示收窄的清单， 模型给出回应后在本会话内恢复完整清单并保持稳定——每会话至多一次清单切换。 只影响给模型看的清单，不改变工具执行的审批边界。对新会话生效。

只读清单含读文件、列目录、搜索等；读写最小对只剩 read_file 和 edit。
「工具调用」更严格：纯文本回答不会解除收窄，直到模型真正动手。

运行护栏

宿主侧硬上限与停止信号：任一触发后，run 会先做一次总结再进入审核，工作区改动保留、绝不自动回滚。

默认 60；模型回合产出工具调用即计 1 轮。

请求构成审计

开启后，每个会话发给模型的请求信封（工具清单、托管工具、输出上限）会写入旁路审计文件， 用于核对请求构成；正式的会话记录不受影响。对新开始的会话生效。

审计文件按会话存放在应用数据目录的 sessions/request-audit/ 下。

实验指引

首轮工具清单锚定

目标是稳定首轮请求形状，而不是永久隐藏工具；配置写入即对新会话生效。

01这是什么

每次发给模型的请求都携带一份「工具清单」（tools 数组：工具名 + 参数说明）。 模型只能从清单里选择工具——清单就是它的菜单，与你的项目文件夹无关。

清单在会话中途变化（托管联网工具启停、收尾总结轮清空等）会带来两个成本： 其一，清单排在对话历史之前，字节级前缀缓存的公共前缀断在清单处，历史要重新计费重算； 其二，第一轮给几十个工具，选择面过大会让模型在还没理解代码时就动用重工具。 锚定把清单变化收敛为受控的一次：首轮收窄 → 晋升后恢复完整 → 会话内不再变。

02三个档位

完整清单默认 · 不锚定
read_fileedit bashsearch …全部

完全现状。随时退回，不产生任何行为差异。

只读清单推荐起步
read_filelist_files searchglob

逼模型首轮先侦察再动手。适合大多数“先理解再改”的开发任务。

读写最小对最激进
read_fileedit

首轮只有读+改的闭环。适合边界清晰的小改动；需要跑命令验证的任务会拖慢起步。

03恢复完整清单的时机

任意首轮回应

模型给出任意 assistant 回复（含纯文本）即恢复完整清单。

默认。首轮收窄很快结束，目录变化几乎无感。
首次真实工具调用

模型必须真正发起工具调用才解除收窄；纯文本寒暄不触发。

更严格：防止“好的我来做”式空谈提前放开清单。

04推荐组合

只读清单 + 任意回应
最平衡，建议从这里开始

首轮只能读/搜/列目录，模型一开口就放开全部工具。适合大多数先理解再动手的任务。

读写最小对 + 工具调用
最激进，边界清晰的小改动

首轮只有 read_file + edit，且必须真正动手才恢复。

注意：需要跑命令验证的任务会被拖慢——首轮无法执行任何命令。

完整清单
随时退回

选择“完整清单 · 不锚定”即回到现状，运行中的会话本就不受影响。

05如何验证效果

  1. 到「设置 → 诊断」打开请求构成审计开关。
  2. 用锚定配置新开会话，跑 2–3 个真实任务。
  3. 打开审计文件，对比第 1 轮与第 2 轮的 tool_names 字段：首轮应是收窄名单，晋升后恢复完整，之后不再变化。
    应用数据目录 / sessions / request-audit / {会话id}.jsonl
  4. 积累一周数据后，比较锚定开/关会话的清单种类数（= 缓存断点预算），再决定是否转正。

06边界与事实

  • 清单裁剪只是呈现层：模型看不见清单外的工具，但工具执行与审批边界原样工作，收窄不等于降低安全要求。
  • 只对新会话生效；运行中的会话不受配置变化影响，也不会被中途换清单。
  • 每个会话至多一次清单切换（收窄 → 完整），不存在反复横跳。
  • 「只读清单」是清单级收窄，与 Ask 模式的只读策略无关；Ask 模式本来就是只读，不受锚定影响。

内容随应用版本内置，与配置行为同源维护；Esc 随时关闭。
