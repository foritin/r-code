# 自托管中继部署方案（R5）

> 配套 [实施计划](./plan.md) 与 [架构说明](./architecture.md) §9。回答“我有云服务器和公网 IP，能否作为中继”——**可以，这是 R5 的标准形态**。本文冻结拓扑、密钥、运维边界；任务清单见 [tasks.json](./tasks.json) R15+。

## 1. 它在整条链路里的位置

```
手机 PWA（任意网络：4G/5G/外网 Wi-Fi）
   │  wss://relay.example.com/device   （出站 443，TLS 公网证书）
   ▼
┌─────────────────── 云服务器（公网 IP，仅这一个暴露面）───────────────────┐
│  r-code-relay：无状态路由 + 限速，不持有任何会话密钥                     │
└───────────────────────────────────────┬─────────────────────────────────┘
                                         │ wss（出站 443，daemon 主动连入并常驻）
                                         ▼
                          家里/办公室的电脑：r-code-service（daemon）
                          └─ 插件执行、本地凭据、工具全部留在这台机器
```

关键性质：

- **只有云服务器暴露在公网**，你的电脑不开放任何入站端口（NAT 友好，无需端口转发、DDNS）；
- daemon 和 PWA 都是**主动出站**，所以公司网/校园网/手机热点都能连；
- 中继**看不到明文**：配对阶段双方经中继协商端到端会话密钥（Noise XX），中继转发的是密文帧；它被攻破只等于“断网”，不等于“被控”。

## 2. 认证与路由（中继能验证什么）

中继只认两类连接，都不涉及插件协议：

| 连接方 | 凭证 | 注册时机 |
| --- | --- | --- |
| daemon（owner） | **owner 注册码**（桌面端生成，一次性引导） | 桌面端配置中继时，daemon 首次上线注册长期 owner 身份（公钥） |
| PWA（device） | **设备令牌**（同局域网配对产物，见 architecture §4） | 扫码/配对码完成后，设备公钥与 owner 绑定 |

路由键：`owner_id → daemon 长连接`；device 帧必须携带已绑定到该 owner 的设备凭证。中继做的事：

1. 维持 daemon 的长连接注册表（内存态，可多实例时用 Redis/共享存储，首期单实例）；
2. 校验 device→owner 绑定关系（签名验证，中继只需公钥）；
3. 字节级双向转发 + 限速/连接数上限；
4. 审计“谁在何时连过”（连接元数据，无内容）。

中继**不做**：解密、命令鉴权（能力校验仍在 daemon 侧）、审批决策、凭据存储、任务数据落盘。

## 3. 端到端密钥协商（经中继的配对）

局域网配对（R2）发生在同一网段；经中继配对时多一跳，但信任根不变：

1. 桌面端生成 owner 身份密钥对（静默读入平台凭据存储），daemon 带着 owner 注册码连中继注册公钥；
2. 桌面端显示 QR：含中继地址、owner id、**一次性配对密语**、daemon 公钥指纹；
3. PWA 扫码 → 经中继与 daemon 跑 Noise XX：daemon 公钥以 QR 指纹钉死（TOFU 同局域网版），配对密语作为**带外认证**防止中继侧冒名；
4. 协商出的会话密钥只存在于 PWA 与 daemon；之后帧载荷端到端加密，中继见到的是不透明二进制；
5. 设备令牌在加密通道内由 daemon 颁发，能力模型（events:read/tasks:write/approvals:decide）完全不变。

## 4. 云服务器要求（很低）

- 一个公网 IP + 域名（Let's Encrypt 免费证书，Caddy/nginx 或 relay 内置 ACME 均可）；
- 最小规格即可：中继是 IO 转发，1 vCPU/512MB 起步；带宽按你的事件/输出流量（工具输出有帧上限）；
- 开放 443；其余不需要；
- 建议：systemd 常驻、非 root 运行、日志轮转、fail2ban/限速在 relay 内置；
- 单实例首期足够（一个 owner 一个 daemon）；多实例横向扩展列为后续。

部署形态二选一（R15 评审定）：

1. **独立小二进制 `r-code-relay`**（`crates/r-code-relay/`，约一个 axum/hyper 服务）——推荐，攻击面最小、可独立更新；
2. 容器镜像（Dockerfile + compose），便于一键上云。

## 5. 安全边界（必须写进实现与文档）

- 中继被攻破的最坏情况：拒绝服务 + 流量元数据泄露；**不能**导致代码执行或凭据泄露（无私钥、无会话密钥）；
- owner 注册码是中继上的最高权限凭证（能注册 daemon 身份）：一次性、短 TTL、只在桌面端显示一次；
- 设备吊销仍由 daemon 裁决：即使中继仍接受该设备连接，daemon 侧能力校验拒绝（纵深防御，不把信任全押给中继）；
- 中继域名/证书是常规公共 TLS（防被动窃听），**防主动冒名靠 QR 指纹 + 配对密语**，两层不混为一谈；
- 默认中继地址为空：不配置就不走中继，产品不内置任何官方中继（除非未来单独立项运营）。

## 6. 与局域网模式的关系

- 同一套设备登记、能力、事件协议；传输是 `IpcTransport` 的第三个实现（管道 / 局域网 TLS / 中继 E2EE）；
- 客户端连接策略：同局域网直连（低延迟），否则回落中继；可配置强制中继；
- daemon 对中继的长连接断线指数退避重连（复用 ensure_daemon/connect 的退避工具）。
