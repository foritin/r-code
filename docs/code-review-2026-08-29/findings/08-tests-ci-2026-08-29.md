## 逐条展开

### F-test-01（major）meta 自测 2/7 不在 CI 且已实际失败

- 证据：ci.yml:31 的 `node --test` 只列 `release / release-quality-gate / flaky-test-report / icon-assets / verify-codex-interaction` 5 个；release.yml 也只引用 release 系脚本。`scripts/verify-product-experience.test.mjs` 与 `scripts/verify-windows-reliability.test.mjs`（连同它们守护的 `docs/product-experience-redesign/{worklist,settings-capability}-gate.json`、`docs/support/contracts/*-migration-gate.json` 与 scripts/product-experience/registry.mjs 的任务注册表）全仓 workflow 零引用。
- 实跑（2026-08-29 本机）：`verify-product-experience.test.mjs` → tests 12 / pass 11 / **fail 1**，失败点 :105 `assert.ok(pending.length > 0, "fixture 需要 M9-04 存在未接线断言")`。根因：M9-04 已在 wiring.mjs:221-222 接线真实执行器（m9-04-checks.mjs），meta 测试赖以成立的「M9-04 存在 not_implemented 断言」fixture 前提已消失——测试腐烂且因不在 CI 无人发现。`verify-windows-reliability.test.mjs` 当前 11/11 通过，但同样无 CI 保护，下一个腐烂只是时间问题。
- 影响：product-experience 42 任务注册表与 redesign gate 文档的一致性守卫形同虚设；这正是「docs/meta 文档由 CI 验证还是纯手工」问题的答案——两个 gate 体系里只有 codex-interaction 一个在 CI。

### F-test-02（major）clippy 门禁无 lint 组

- 证据：`find -maxdepth 2 -name clippy.toml` 零命中；`grep "\[lints\]" Cargo.toml`（workspace + src-tauri + 全部 crates）零命中；ci.yml:135 仅为 `cargo clippy --workspace --all-targets -- -D warnings`（默认 lint 集）。
- 量化：仅 src-tauri/src/commands.rs 一个文件 1221 处 `.unwrap()`；workspace `Cargo.toml:142` `panic = "abort"` 使生产路径 unwrap 直接进程终止。测试代码中的 unwrap 会把「夹具构造失败」伪装成断言失败（栈指向 unwrap 而非意图），降低可诊断性。
- 与 RV-03（correctness 维度）的 unwrap 纪律发现互为印证：本条从 CI 门禁角度补充——即便代码纪律好，门禁层没有任何强制。修复不必一步到位：先 `[lints] clippy::unwrap_used = "warn"` 跑基线，再按目录收敛。

### F-test-03（major）flaky 探测与门禁配置漂移 + 无 quarantine 闭环

- 证据：ci.yml:198-200 注释自述「多个 workspace 集成套件共享进程级全局 fixture，串行避免 CI 负载下的平台相关假挂起」并以 `--test-threads=1` 门禁；flaky-tests.yml:88-94 同一命令却**不带** `--test-threads=1`。后果两向：flaky 报告里的失败可能是门禁永不复现的并行竞争（信噪比问题）；门禁串行掩盖的竞争则只在周一报告出现且 classifyAttempts（flaky-test-report.mjs:80-90）只标记 `flaky-candidate` 上传 artifact，无 issue 创建、无 PR 阻断、无重试豁免名单——quarantine 机制不存在。
- 补充：frontend 腿 `npm test` 内部 `--test-concurrency=1`（run-tests.mjs:33）两边一致，无此问题。

### F-test-04（major）0 个 #[ignore]、已知失败无机制化处置

- 证据：`grep -rn '#\[ignore' src-tauri crates` = 0 命中（含 `#[ignore = "..."]` 变体）。前端 `grep '.skip('` 亦零命中。仓库根遗留日志显示最近一次 CI 抓取（2026-08-23）双红：ci-frontend-meta.log 前端套件 202 测 198 过 **2 败**（`saved providers auto-sync models on open...`、`session strip exposes mutually exclusive step/change popovers...`）；ci-ubuntu-test.log Rust `plan_eval.rs:1920 dry_run_collects_profile_without_starting_a_provider_run_or_leaking_secrets` FAILED（"dual-track arm froze an unexpected runtime profile"）。叠加工作记忆中 app-shell 本地 6 失败：三类已知失败都没有 ignore 标记、quarantine 目录或追踪文件。
- 双刃性说明：零 ignore 也意味着零静默跳过（优点，与「修复消除根因、禁止压告警」的仓库公约一致），本条 severity 定 major 是因为「已知失败」的处置路径缺失而非要求引入 ignore——至少需要文档化的 triage 记录。

### F-test-05（minor）金集 slow 档无门禁

corpus.jsonl 44 条中 3 条 tier=slow（slow-sleep-ok `sleep 2 && echo`、slow-exit-1 `sleep 1; exit 1`、slow-chain `sleep 1 && echo step-a && sleep 1 && echo step-b`）。ci.yml:206 仅 `--tier fast`（41 条，预算 <2min 注释可考）。slow 档验证的长时命令退出码捕获与两段流式输出无回归保护；全仓无 `--tier slow|--tier all` 的 workflow 引用。3 条总量小，放进每日或 flaky 腿成本可忽略。

### F-test-06（minor）CORPUS_RUN 静默 skip 掩盖非 Windows 零执行

command_corpus_runner.rs:233-243：未设 `CORPUS_RUN` 时测试函数打印提示并 return（记 passed 而非 ignored）。因此 ubuntu/macos 腿 `cargo test --workspace --all-features` 的绿灯里金集执行数为 0，从测试总结无法察觉。registry.mjs:49-58 的 note 自述 darwin 基线报告需 macOS 主机手工产出后断言才转 implementation 复检——unix 侧命令可靠性目前是「手工证据」而非门禁。最小修复：skip 时用 `#[ignore]` 风格显式计数，或在 CI 腿加 `platform` 过滤子集运行。

### F-test-07（minor）22/61 前端测试为源码 regex 断言

分类方法：文件内 `chromium.launch|newPage|newContext` 零命中且主体为 `readFileSync(src/**.tsx) + assert.match` 判为纯静态。22 个文件符合（automation-contract、browser-contract、companion、model-switcher、subagent-provider-autoprobe、m1-*/m2-03-a4/m4-01/m4-03 系列等）。示例：model-switcher.test.mjs:19 断言 `/\.filter\(\(choice\) => choice\.ready\)/`——把「过滤 ready」这一行为钉死在具体链式调用文本上，等价重写（如提为命名函数）即假阳性；反之组件运行时回归（ready 判断写错）只有 Playwright 层能抓，而 Playwright 全量只在 ubuntu 腿。静态层并非无价值（防能力面回退、零环境依赖），问题是占比 36% 且无标注区分。39 个动态测试质量好：app-shell 95 test/584 assert，companion-window-ui 107 assert。

### F-test-08（minor）平台分工盲区与名不副实的 Windows 契约名单

- Windows 前端腿（ci.yml:196）跑 app-shell/companion-window-ui/companion 三文件并注释称「宿主 OS 行为契约」，但 companion.test.mjs 全部为 `fs.readFileSync` 静态断言（含读 `../src/main.rs` 与 `../capabilities/companion.json`），与宿主 OS 无关——真正需要 Windows 的混合 DPI/OCR 契约在 app-shell 与 companion-window-ui 内。名单颗粒度错位，无实际风险但误导维护。
- 反向盲区：`lib.rs:20` `#[cfg(unix)] pub mod control_door`（34 测）、`lib.rs:28` `#[cfg(target_os = "macos")] mod mac_ocr`（3 测）在本地 Windows `cargo test` 中不编译不运行且无任何提示；CONTRIBUTING.md:69 只给 `cargo test --workspace --all-features` 一条命令，未说明平台差异。CI 三腿矩阵本身覆盖了这些测试（unix 测在 ubuntu/macos 腿跑，windows_ocr 3 测在 windows 腿跑，含一条真实 Windows OCR 引擎对 fixture 的识别测试），矩阵分工是健全的，缺的是文档。
- verification.rs 展示了正确范式：同一测试逻辑 + 平台自适应命令夹具（`successful_command()` 在 windows 用 `exit /B 0`、unix 用 `true`，:537-565）。

### F-test-09（minor）固定 sleep 等待（无 >1s，风险低）

全测试代码 `sleep(` 共 31 处：llm_runtime_tests.rs 27 处（5/10/20ms 事件泵推进 + :6438 一处 300ms）、final_delivery.rs:438 250ms、health_check.rs:26,45 各 50ms、control_integration.rs:57 40ms。无超过 1s 的固定等待；control_integration 使用 40ms 轮询循环模式。整体卫生好于绝大多数同类仓库。残余风险：300ms 固定等待在慢 runner 高负载下的竞态窗口，建议换条件轮询。

### F-test-10（minor）flaky 探测缺 ubuntu Rust 腿且频率周级

flaky-tests.yml:75 rust matrix = [macos-latest, windows-latest]，无 ubuntu——而 ubuntu 恰是门禁 cargo test 与全量前端的主腿。cron `17 3 * * 1` 每周一次，工作日引入的时序 flake 平均 3.5 天不可见。frontend 腿（ubuntu+windows）与 rust 腿的不对称没有注释说明。
