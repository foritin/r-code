## 逐条展开

### F-robust-01 codex app-server 退出在 Windows 留整棵孤儿进程树（blocking）

- 位置：`src-tauri/src/codex_app_server.rs:771-797`（codex_app_server_command：非 .exe 路径走 `cmd.exe /D /S /C call <codex> app-server`）、`:598-604`（shutdown：`self.writer.take(); let _ = self.child.kill().await; let _ = self.child.wait().await;`）、`:817`（kill_on_drop 同样只覆盖直接子进程）。
- 触发：npm 安装的 codex CLI（codex.cmd shim，默认安装形态）+ 任一次会话结束/插槽回收/应用退出（main.rs:978 `codex_app_server.shutdown()` → reclaim_app_server_slot → transport.shutdown）。
- 后果：cmd.exe 被 TerminateProcess，codex node 进程及其拉起的 MCP server/shell 后代全部存活，持有工作区文件锁、端口、会话状态，跨次运行累积。
- 为什么没有这层保护：transport 抽象层（CodexAppServerTransport）只持有 tokio Child，不知道"Windows wrapper 进程"语义；树杀知识散落在 commands.rs 的 CLI 交互层（terminate_codex_child）与 gateway 层（kill_tree），未提炼为共享工具。
- 修复：shutdown 前按 pid 调 `taskkill /PID <pid> /T /F`（成功即返回，失败回落 kill()），Unix 侧 process_group(0) 已配置（:804-809，kill 负组 id）。

- 触发面更宽：MCP 桥接取消（codex_mcp.rs:97-99）、失败重建（:105-107）、连接超时清理都会走 shutdown。
- 修复同 F-robust-01。

### F-robust-03 一次性 codex/npm CLI 超时路径的后代泄漏（major）

- 位置：`src-tauri/src/commands.rs:17030-17058`（codex_command_at + run 处 `timeout(deadline, command.output())`）、`:17063-17099`（npm 同型）。
- 机理：超时使 `output()` future 被 drop，Child 随之 drop，kill_on_drop 只 TerminateProcess cmd.exe；正在运行的 `codex login/sync`、`npm install` 的 node 后代存活。与同文件 20737-20760（terminate_codex_child，注释明确"taskkill /T 回收 .cmd wrapper 与 Node 后代"）形成直接对照——保护存在但未覆盖此路径。
- 修复：不用 `output()`，改为 take stdout/stderr + spawn drain + `child.wait()` + select 超时后 taskkill /T（tools_command.rs:596-637 的成熟模板）。

### F-robust-04 Anthropic 线路 SSE 无空闲 watchdog（major）

- 位置：`vendor/agent-contracts/crates/agent-llm/src/anthropic.rs:254-271`（do_stream：`parse_sse_stream(byte_stream, ...)`，无 watchdog）；客户端构造 `:56-60` 仅有 `connect_timeout(15s)`，无总超时/读超时。
- 对照：openai.rs:392-397 与 responses.rs（经 `parse_openai_sse_with_idle_timeout`）都有 `DEFAULT_STREAM_IDLE_TIMEOUT=120s` 的 `watch_sse_idle` 字节级 watchdog，超时以可恢复的 `stream_idle_timeout` 终止并允许 agent 层冻结重放（agent_loop.rs:1090-1155）。
- 实际兜底：agent_loop.rs:35 `LLM_PROVIDER_IDLE_TIMEOUT = 600s` 包住 `stream.next()`（:917/:931）。即 anthropic 线路一次事件间隔最多容忍 10 分钟，最坏 5 次重放（MAX_STREAM_RECOVERIES=5）累计 ~50 分钟才浮出错误；网络切换/NAT 超时场景用户体验显著差于 openai 线路的 120s。
- 为什么没有：watchdog 实现放在 openai.rs 模块内（`watch_sse_idle`），anthropic.rs 独立实现了 `parse_sse_stream`，未共享该基础设施。
- 修复：把 `watch_sse_idle` 提为 crate 级工具，anthropic do_stream 套用同一 120s。

### F-robust-05 子代理报告浓缩调用无超时（major）

- 位置：`crates/r-code-agent-worker/src/llm_runtime.rs:10260-10309`（prepare_subagent_report），`:10298` `provider.complete(request)` 后的 loop 仅在 `PARENT_ABORT_BRIDGE_POLL`（50ms）里检查 `is_child_cancelled`。
- 挂死链：vendor complete() 在 `send_with_retry` 拿到 200 响应头后进入 `resp.json().await`（anthropic.rs:245 / openai.rs:359-362），reqwest 无总超时 → 网关停 body 即永久 Pending → 父循环 `wait_for_subagent`（:10536-10549）watch 无新值同步挂住 → 子代理 join 槽占用。
- 解除条件只有用户主动 Stop（父 abort）。对照：同类 complete() 调用在 compaction（commands.rs:3325-3341，120s）、自动压缩（llm_runtime.rs:3205-3224，120s）、视觉检查点（:3922 VISUAL_CHECKPOINT_TIMEOUT）、图像理解（commands.rs:7118-7121，60s）、memory review（memory_runtime.rs:84-102，120s）、槽位探测（commands.rs:16293）都有 deadline——唯独此处遗漏。
- 修复：套 120s timeout，超时走既有 `fallback_subagent_report`（:10320-10331 已有降级路径）。

### F-robust-06 drain loop 无 panic 兜底，失败后状态机卡 running（major）

- 位置：`src-tauri/src/commands.rs:8675-9067`（spawn_drain_loop_with_resources），`:8691` `tokio::spawn(async move {...});` JoinHandle 丢弃；终态收敛全部在任务尾部（`native_run_terminal_outcome` 分支的 mark_run_aborted/update_state、`:9036-9046` 的 `bridge.active = None` / `closing_run_id` 清理）。
- 失败场景：任务体内任意 panic（F-robust-07 的锁中毒是最现实的放大器；gateway 已隔离工具 panic，但 drain loop 自身的 DB/投影/桥接代码无保护）→ tokio 吞掉 panic → run 在 DB 中 `ended_at IS NULL`、任务 state 停在 running、bridge.active 永占 → UI 永久"运行中"，同任务后续 send 进队列不派发；只能重启应用由启动恢复收束。
- 为什么没有：正常运行路径（完成/失败/中止）都有显式终态分支并经过测试；panic 路径依赖"tokio 不传播 panic"默认行为，未视为状态机输入。
- 修复：spawn 外包一层 `AssertUnwindSafe` + catch_unwind 驱动的 finalize（或 ActiveRun 的 Drop guard：构造时注册，正常路径显式 disarm，Drop 时若未 disarm 则落 Interrupted + mark_run_aborted + 事件）。

### F-robust-07 llm_runtime 13 处锁中毒即 panic（minor，与 F-robust-06 叠加升维）

- 位置：见总表；典型 `:2141` `.expect("subagent candidate pool lock poisoned")`、`:7345` subagent activity permit、`:8974` subagent join slot、`:128` name allocator。
- 机理：std Mutex 持有者 panic → 中毒 → 运行主路径每次 lock 直接 panic；由于这些代码运行在 drain loop 任务内（F-robust-06），一次中毒 = 该任务卡死且重复触发。
- 修复：低争用场景换 tokio::sync::Mutex（运行时已是 async）；或统一封装 `lock_or_rebuild`。至少对 join slot / permit 这类可重建状态不应 panic。

### F-robust-08 应用退出未收束终端 PTY（minor）

- 位置：`src-tauri/src/main.rs:971-988`（RunEvent::Exit 只处理 mcp_manager + codex_app_server）；TerminalManager（crates/r-code-terminal/src/manager.rs:128-135 有 Drop guard，但 Tauri managed state 在进程退出时不保证析构）。
- 风险：ConPTY 句柄随进程关闭通常导致附着进程退出，但这是 OS 行为而非合同；shell 内运行的孙进程（如 cargo build）可能残留。
- 修复：退出钩子追加 `terminal_manager.kill_all()`（有界 2s）。

### F-robust-09 重试退避无抖动（minor）

- 位置：`vendor/agent-contracts/crates/agent-llm/src/openai.rs:487-496`（backoff_delay；注释明确"未加抖动（无 rand 依赖）"），anthropic.rs 复用同一函数。
- 影响：单客户端场景可接受；用户同时开多任务并发撞 429 时存在同步重试波峰。retryable_status=408|429|500..=599（:483-485）与 Retry-After 尊重逻辑本身正确。
- 修复：以 `SystemTime::now()` 纳秒做 ±20% 抖动即可，无新依赖。

### F-robust-10 MCP 半死会话不驱逐（minor）

- 位置：`crates/r-code-mcp/src/runtime.rs:296-319`（call 失败仅 publish Error 状态）；`ensure_session`（:379-394）只在 `is_closed()` 为真时重连；`is_closed` 直接透传 `peer.is_transport_closed()`（client.rs:506-508）。
- 场景：stdio MCP server 进程僵死（未退出但不再响应，EOF 未产生）时 is_closed 恒 false，工具调用连续失败且不会自动重建会话；状态页显示 Error 但每次调用仍走死会话。
- 修复：call 失败（非取消类）后主动 close_slot_session 一次；或对同 slot 连续 N 次失败强制重建。

- 重试设计：vendor send_with_retry 仅在响应头前重试（body 字节复用，幂等安全），MAX_RETRIES=10、500ms 指数封顶 15s、Retry-After 封顶 60s；错误体读取有 10s 硬超时（openai.rs:511-516）。agent 层 stream replay 仅在"零输出"时重放（幂等安全）、≤5 次、退避可被 abort 打断（agent_loop.rs:1090-1155）。
- 进程内工具 panic 隔离：gateway.rs:443-474 CatchUnwindFuture 在 poll 边界捕 unwind，panic 折成 is_error 工具结果，不杀会话。

- 启动恢复：capture_startup_recovery（commands.rs:1404-1442）+ cleanup_recovery_snapshot（:12034-12140，单事务收束 run/tool_call/task/permission，防重入条件完备）+ reconcile_tool_calls_for_finished_runs（:1378-1398）；migrations 每迁移一个 Immediate 事务 + 版本校验 + FK 恢复（migrations.rs:117-169）。
- 前端：ipc.ts:172-185 统一错误规范化；抽样组件（MemoryPanel.tsx:106-116 等）均为 try/catch/finally + error state；poll.ts 轮询有防重入与失败上报，不会因后端错误卡 loading。
