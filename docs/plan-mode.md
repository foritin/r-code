# Plan 模式、人工确认与增强审核

本文描述 R-Code 的 Plan 工作流及其安全边界。它面向使用者和维护者，并以当前代码与测试为准。

## 工作流

1. 在输入框的“添加”菜单中开启“目标”，直接在主输入框里填写；点击发送会持久化目标并立即启动 Agent，不存在“先保存目标、再另写第一轮要求”的中间态。普通新对话的首条任务描述不会被误标为已设置目标，旧会话升级后也默认没有显式目标。目标模式可通过输入框底部的“× 目标”标签退出。目标运行中可在输入框上方编辑、停止/继续或删除。
2. 原生 R-Code Agent 只使用只读工作区工具调查需求；Plan 模式禁止写文件、Shell、变更型 MCP 和子智能体委派。
3. 信息不足时，Agent 通过 `request_user_input` 提交一组结构化问题。每组包含 1–3 个问题，每个问题包含 2–3 个互斥选项，也允许单独填写自由文本；用户还可以跳过整组问题。
4. 问题落库后当前 Run 立即进入等待状态。运行时拒绝该 Run 后续工具调用，也不会提前执行质量复核或产生“审核就绪”状态。
5. 回答会使用幂等键原子保存，并继续同一任务的 Plan 会话；失败的 continuation 可以显式重试。
6. Agent 发布 Plan 草案。事项必须按可验收的可执行叶子功能拆分，可声明真实依赖；可用 `section_path` 组织阶段和子阶段，UI 与投影会生成 1、1.1、1.2 等编号，父标题本身不是待办。
7. 用户确认实施后，R-Code 固定批准的 Plan 修订，将事项转换为待办，并通过持久队列交给实施运行时。任务模式、唯一队列消息和派发状态在同一 SQLite 事务中落库；应用退出后可从队列恢复，失败时可在 Plan 面板显式重试。

Plan v1 只由原生 R-Code Agent 执行。Codex CLI 可以在普通执行阶段按设置作为协作子智能体使用，但不能作为 Plan 主运行时，以免绕过宿主的暂停与幂等协议。

产品交互只展示 **Agent** 与 **Plan** 两种模式。持久层中的 `ask`、`edit`、`auto` 是兼容和执行策略，不是三个额外的用户模式；工作区权限与主 Agent 选择也分别独立。Agent 可在任何写入前调用宿主工具安全切入 Plan，宿主会原子创建 Plan 并续接同一请求；Plan 只有在用户确认后才切回 Agent 实施。各模式只暴露当前状态合法的生命周期工具，因此 Agent 不会再误调用 `plan_publish`。

## 持久化与文件位置

SQLite 是 Plan、问题、回答、事项、变更归属和审核决定的唯一权威状态源。每个 Plan 使用随机、稳定的 ID；模型提供的功能 ID 和问题 ID只在各自 Plan/问题集内有意义。

右侧 Plan 工作台实时汇总完成、进行中、待处理、阻塞与失败数量。进度分母只包含可执行叶子事项；层级父标题不参与进度或依赖状态。实施过程中，只要 SQLite 仍存在当前 `in_progress` 事项，运行时就会拒绝模型提前以普通回复结束，并要求它完成验收后调用 `plan_item_update`。当前事项内部互不冲突的只读调查与验证可以并行委派给最多三个子智能体，主 Agent 必须收集结果后再更新事项；可能重叠的写入仍保持单一写入所有者。

为了便于用户查看，R-Code 在操作系统应用数据目录生成只读友好的 Markdown 投影：

```text
<AppData>/r-code/plans/<plan-id>/plan.md
```

同一个 Plan 的后续修订始终覆盖自己的稳定投影，不会覆盖其他 Plan。投影写入使用同目录临时文件与原子替换；失败只记录投影错误，SQLite 状态仍可通过“修复投影”恢复。Plan 文档不会写入项目目录，也不会进入项目 Git。

用户可以取消尚未结束的 Plan。取消会终止待处理问题、未完成事项和后续实施派发，并把任务恢复为与工作区相符的普通模式；它**不会**撤销已经写入工作区的文件。若当前仍有主运行或增强审核回滚，取消会 fail-closed，要求先结束该操作。取消后再次进入 Plan 模式会生成新的 Plan ID 和独立投影，不会复用旧计划。

## 普通审核与增强审核

审核面板提供两个互不混淆的视图：

- **普通**：以当前工作区的 Git 变更为边界，按文件/行接受或拒绝；遵守 `.gitignore`。接受只更新 R-Code 审核账本，不会自动 `git add`、commit 或 push。
- **增强**：只显示当前已批准 Plan 的功能变更，按功能分组。用户可以接受/拒绝一个功能中的单个文件，也可以处理整组功能；与该 Plan 无关的 Git 变更不会出现在这里。

如果当前任务没有对应的功能 Plan，增强视图明确保持为空，并提示改用“普通”视图查看工作区变更；它不会把普通任务、Shell、MCP 或外部代理产生的修改猜测为某个功能点。

增强审核在可信写工具完成时记录文件的 before/after 内容快照，并把事件绑定到宿主当前功能事项。功能仍在 `in_progress` 或可恢复的 `blocked` 状态时可以实时查看差异，但接受与拒绝保持禁用；只有功能进入不可再写入的 `completed`、`failed` 或 `cancelled` 后才能形成最终决定，避免已接受的功能继续追加未审核写入。`blocked` 表示计划暂停：在模型通过 `plan_item_update(in_progress)` 显式恢复该事项前，可信写工具同样 fail-closed，不会把新写入错误归给普通审核或其他功能。

直接使用 R-Code 的 `edit`、`apply_patch`、`create_file` 和 `delete_file` 才能获得这类可信归属。Shell、MCP、外部代理或其他无法可靠归属的写入不会伪装成某个功能的变更，只会进入普通 Git 审核。

同一文件可以由多个功能交错修改。拒绝功能 A 时，R-Code 使用 A 的 after、当前文件和 A 的 before 做逆向三方合并，因此只撤销 A 能证明拥有的改动，并保留功能 B 的后续改动。发生冲突时操作 fail-closed：文件保持不变，界面要求用户手动处理。

## 并发、恢复与数据安全

- 数据库事务不跨越模型等待或文件 I/O。
- 同一路径的写入捕获与拒绝操作共用进程内路径协调器；多文件操作按规范化路径排序取锁，避免锁顺序反转。
- 多文件拒绝先计算所有目标；任意文件冲突时不修改任何文件。
- 写入前保存 durable rejection journal 和 rollback blob。若中途 I/O 失败，已写文件会按 journal 回滚；应用重启会恢复未完成操作。
- 工作区路径会重新规范化并检查边界；既有文件的读取、替换和删除通过创建时固定的工作区目录 capability 执行，Plan 的跟踪写入包装器会把该 capability 继续传给内层工具，符号链接不能把操作目标带出工作区。
- Blob 引用和审核账本保存在 AppData，项目目录中不创建 R-Code 私有记忆或 Plan 元数据。
- 永久删除会话或忘记项目时，R-Code 在事务内按真实引用计数释放 Plan 审核 Blob，再按可信的 UUID 目录清理 Plan 投影；启动时会重试清理未被数据库引用的孤儿文件。数据库中的投影路径不会作为删除目标。

## 状态概览

Plan 状态依次为 `draft`、`awaiting_input`、`ready` 和 `executing`，最终进入 `completed` 或 `cancelled`。确认实施通过一次原子操作固定批准修订、激活首个功能点并直接进入 `executing`；持久化契约中的 `approved` 值只为兼容恢复边界保留，正常流程不会让 UI 停留在该状态。功能事项使用 `proposed`、`pending`、`in_progress`、`blocked`、`completed`、`failed`、`cancelled`。UI 展示的是 SQLite 中的当前状态，不从 Markdown 投影反向推断状态。
