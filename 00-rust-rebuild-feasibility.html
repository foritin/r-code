Charter Rust 重构可行性分析

概述

本文档从技术角度全面评估使用 Rust 重构 Charter 桌面应用的可行性，
包括架构设计、技术选型、工作量估算和风险评估。

1. 重构目标

  • 保留现有功能完整性
  • 提升性能表现
  • 增强内存安全性
  • 降低资源占用
  • 维持跨平台能力（macOS / Windows / Linux）

2. 技术选型

2.1 桌面框架

选择：Tauri v2

2.3 Agent 运行时方案

由于当前 Pi SDK 为 JS/ESM+wasm 专用，存在三条可选路径：

  • 路径 A：使用 deno_core 或 rquickjs 嵌入 JS 运行时，直接加载 Pi SDK
  • 路径 B：自行封装 LLM 调用与工具定义，重写 Agent 运行时
  • 路径 C：通过 MCP 协议解耦，Agent 作为独立二进制通过 MCP 与宿主通信

路径 C 最为优雅，但依赖生态支持；路径 A 兼容现有 SDK 但复杂度高。

3.2 IPC 机制

使用 tokio::net::UnixStream（macOS/Linux）或 Named Pipe（Windows）
替代 Electron 的 MessagePort。协议采用 JSON-RPC 2.0 风格，
使用 serde 进行序列化/反序列化。

5. 收益分析

5.1 性能提升

  • 二进制大小减少约 90%
  • 启动速度显著提升
  • 内存占用大幅降低
  • CPU 密集型任务（如 Replay 解析）性能提升明显

5.2 安全性增强

  • 内存安全由编译器保证（消除 use-after-free、buffer overflow 等）
  • 进程隔离模型保持不变
  • 权限引擎逻辑不变，但实现更可靠

5.3 维护性

  • 类型系统更强大，运行时错误减少
  • 依赖管理更清晰（Cargo）
  • 但 Rust 学习曲线较陡

6. 风险评估

6.1 高风险

  • Pi SDK 无 Rust 绑定：Agent 运行时是唯一无现成方案的部分
  • MCP 生态成熟度：Rust 的 MCP SDK 不如 JS 版完善

6.2 中风险

  • Monaco Editor 集成：Web 组件在 Tauri WebView 中的深度集成需重新适配
  • 测试基础设施：Playwright Tauri 适配器不如 Electron 版成熟
  • 跨平台构建：macOS/Windows 交叉编译 CI 复杂度增加

6.3 低风险

  • Tauri 框架本身成熟稳定
  • 系统级操作 crate 均已生产就绪
  • 渲染层 React/TS 代码大部分可复用

7. 建议实施路径

7.1 原型阶段（2-4 周）

  1. 使用 Tauri 搭建最小可用骨架
  2. 实现基础 IPC 通信
  3. 验证 React 渲染层在 WebView 中的运行

7.2 核心迁移阶段（2-3 月）

  1. 优先迁移 Tool Gateway 和 Permission Engine
  2. 迁移持久化层和 Git 服务
  3. 迁移 PTY 终端服务

7.3 Agent 集成阶段（1-2 月）

  1. 确定 Agent 运行时方案（建议路径 C：MCP 解耦）
  2. 实现 Agent Worker 进程
  3. 实现与 Tool Gateway 的 IPC

7.4 验证阶段（1-2 月）

  1. 完整测试覆盖
  2. 性能基准对比
  3. E2E 验证

8. 结论

技术上完全可行，但工作量大、周期长。 这不是简单的"重写"，
而是"重新构建一个新产品"。建议作为独立项目推进，
而非在当前产品上直接替换。

本页为可离线浏览的重构规范；代码示例是实现合同，不是已交付源码。
