第 6 章：终端系统

第 4 章我们深入了 PTY 的底层原理——Master-Slave 对、Line Discipline、ConPTY vs Unix PTY。本章则从产品视角出发，讲解 R-Code 如何把这些底层原语组装成一个多终端、可观测、可编排的终端系统。

6.1 本章定位

第 4 章讲的是「PTY 是什么」，本章讲的是「R-Code 怎么用 PTY」。两者的关系就像「发动机原理」和「汽车工程」：

终端系统的核心模块分布在 crates/r-code-terminal/：

  • manager.rs —— 多终端生命周期管理
  • block.rs —— OSC 133 块解析
  • shell_integration.rs —— Shell 集成注入

6.2 TerminalManager 多终端管理

TerminalManager 是终端系统的入口。它负责管理多个 PTY 终端实例，每个实例都有独立的子进程、读写管道和 scrollback 缓冲区。

pub struct TerminalManager {
    pty_system: Box<dyn PtySystem + Send>,
    terminals: Arc<Mutex<HashMap<TerminalId, TerminalHandle>>>,
}

你可以把 TerminalManager 想象成一个「终端公寓大楼」：

  • 大楼本身（TerminalManager）负责整体管理
  • 每个房间（TerminalHandle）有独立的住户（shell 进程）和信箱（scrollback 缓冲区）
  • 门牌号（TerminalId）是每个房间的唯一标识

创建一个新终端

pub async fn create(
    &self,
    shell: &str,           // 比如 "/bin/zsh"
    working_dir: &Path,    // 比如 "/home/user/project"
    env: Vec<(String, String)>, // 额外环境变量
) -> Result<TerminalId, ProductError>

创建流程的内部步骤：

① pty_system.openpty(PtySize::default()) │ ▼ ② pair.slave.spawn_command(cmd) ──→ 子进程（shell）启动 │ ▼ ③ pair.master.take_writer() ──→ 获取 stdin 写入器 │ ▼ ④ pair.master.try_clone_reader() ──→ 克隆 reader │ ▼ ⑤ drop(pair.slave) ──→ 关闭 slave 引用 │ ▼ ⑥ 后台线程持续读取 PTY 输出 ──→ unbounded channel 传递 │ ▼ ⑦ 组装 TerminalHandle，插入 HashMap
💡 为什么 drop(slave)？

关闭我们的 slave 引用后，当子进程退出时，master reader 能收到 EOF。如果不 drop，master 会一直等待，因为「还有一个人拿着 slave 的把手」。

6.3 TerminalHandle 完整状态

每个终端实例由一个 TerminalHandle 表示，它包含了管理一个终端所需的所有状态：

pub struct TerminalHandle {
    pub id: TerminalId,               // 唯一标识（UUID）
    pub state: TerminalState,         // 当前状态
    pub shell: String,                // shell 路径
    pub working_dir: PathBuf,         // 工作目录
    pub scrollback: Vec<u8>,          // 滚动缓冲区（ANSI-stripped）
    child: Box<dyn Child + Send + Sync>,     // PTY 子进程
    writer: Box<dyn Write + Send>,           // PTY stdin 写入器
    master: Box<dyn MasterPty + Send>,       // PTY master
    output_rx: mpsc::UnboundedReceiver<Vec<u8>>, // 后台读取通道
    killed: bool,                     // 是否已被显式 kill
}
字段作用类比
id唯一标识，用于 API 调用门牌号
state当前终端状态（见状态机）房间状态牌
shell使用的 shell 类型住户姓名
working_dir当前工作目录房间位置
scrollback输出历史缓冲区信箱/留言本
child子进程句柄（用于 kill / wait）房东联系方式
writer向 stdin 写入数据投递口
masterPTY master（用于 resize）总控台
output_rx后台读取通道收件箱
killed防止 Drop 重复 kill已退房标记

Drop 实现：防止孤儿进程

impl Drop for TerminalHandle {
    fn drop(&mut self) {
        if !self.killed {
            // 确保子进程被终止和回收，避免孤儿进程
            let _ = self.child.kill();
            let _ = self.child.wait();
        }
    }
}

当一个终端被关闭或Manager 被销毁时，Drop 会自动 kill 子进程并等待它退出，防止产生孤儿进程。

6.4 终端状态机

每个终端在任意时刻都处于四种状态之一。注意这些状态并非严格的线性转换——Agent 是独立于 Busy 的检测状态，从 Idle 可以直接进入 Busy、Agent 或 Exited：

pub enum TerminalState {
    Idle,     // Shell 正在运行，等待输入
    Busy,     // 命令正在运行
    Agent,    // 检测到外部 CLI agent（claude/codex）
    Exited,   // 终端已退出
}
┌──────┐ spawn ┌──────┐ 命令开始 ┌──────┐ │ │ ──────────→ │ IDLE │ ──────────→ │ BUSY │ │ init │ └──────┘ └──┬───┘ └──────┘ ▲ │ │ 命令结束 │ 检测到 agent │ ▼ │ ┌──────┐ │ agent 结束 │AGENT │ └─────────────── └──────┘ │ ▼ ┌──────┐ │EXITED│ └──────┘

状态检测逻辑

状态检测通过轮询子进程的存活状态实现：

  • Idle —— 子进程存活，且没有前台命令在运行
  • Busy —— 子进程存活，且有前台命令在执行中（通过 OSC 133 D 标记判断）
  • Agent —— 子进程存活，且检测到外部 CLI agent 进程
  • Exited —— 子进程已退出

6.5 OSC 133 Block 解析器

R-Code 使用 OSC 133（iTerm2 Shell Integration 协议）来追踪终端里命令的执行边界。这个协议通过在 shell 的提示符前后插入特殊的转义序列，让程序可以知道「哪段输出属于哪条命令」。

OSC 133 标记类型

标记含义触发时机
A (PromptStart)提示符开始shell 显示提示符前
B (PromptContinuation)提示符结束，命令输入开始用户开始输入命令时
C (CommandExecuted)命令已执行，输出开始命令开始执行时
D;exit_code (CommandExit)命令退出命令执行完毕时

BlockParser 实现

pub struct BlockParser {
    current_block: Option<Block>,     // 当前正在解析的块
    blocks: Vec<Block>,               // 已完成的块列表
    state: ParseState,                 // 解析状态
    pending: Vec<u8>,                  // 不完整转义序列的暂存区
}

解析器的核心是一个状态机，在四种解析状态之间切换：

┌──────────┐ OSC 133;A ┌──────────┐ OSC 133;B ┌──────────┐ │ Outside │ ─────────────→│ InPrompt │ ─────────────→│InCommand │ └──────────┘ └──────────┘ └────┬─────┘ ▲ │ │ │ OSC 133;C │ ┌──────────┐ ▼ │ OSC 133;D │ InOutput │ ┌──────────┐ └──────────────────│ │←─────────────────│ (输出中) │ └──────────┘ └──────────┘

两种块类型

pub enum BlockType {
    Command,   // 命令块：prompt → command → output → exit code
    Turn,      // Turn 块：外部 Agent 会话边界
}

每个 Block 包含：

pub struct Block {
    pub block_type: BlockType,
    pub command: Option<String>,     // 执行的命令
    pub output: String,               // 命令输出
    pub exit_code: Option<i32>,      // 退出码
    pub started_at: DateTime<Utc>,
    pub ended_at: Option<DateTime<Utc>>,
}
✅ 跨 feed 处理

BlockParser 能够处理转义序列被分割在多次 feed() 调用中的情况。不完整的序列会被暂存在 pending 字段中，等下次 feed() 时继续解析。

6.6 Shell Integration 注入

要让 OSC 133 协议工作，需要在 shell 启动时注入相应的配置。shell_integration.rs 负责根据 shell 类型生成正确的参数和环境变量。

pub fn shell_integration_spawn(config: &ShellIntegrationConfig) -> ShellIntegrationResult {
    match shell_name {
        "zsh" => spawn_zsh(),
        "bash" => spawn_bash(),
        "fish" => spawn_fish(),
        "powershell" | "pwsh" => spawn_powershell(),
        _ => ShellIntegrationResult { args: vec![], env: vec![] }, // 降级
    }
}

各 shell 的注入策略

Shell策略实现方式
zshZDOTDIR shim创建临时目录，.zshrc 注册 precmd/preexec hooks
bash--init-file shim创建临时脚本，安装 PROMPT_COMMAND + DEBUG trap
fishXDG_DATA_DIRS prepend使用 fish_prompt/fish_postexec 事件处理器
PowerShell-File 脚本覆盖 prompt 函数，使用 PSReadLine 的 AcceptLine 事件
其他 / 禁用降级无 OSC 133 标记，仅依赖 scrollback

zsh 集成示例

// zsh 集成：设置 ZDOTDIR 到临时目录，.zshrc 注册 OSC 133 hooks
fn spawn_zsh() -> ShellIntegrationResult {
    let zdotdir = std::env::temp_dir()
        .join(format!("r-code-zsh-{}", uuid::Uuid::new_v4()));
    fs::create_dir_all(&zdotdir);

    let zshrc = r#"# R-Code shell integration for zsh
if [[ -n "$R_CODE_USER_ZDOTDIR" && -f "$R_CODE_USER_ZDOTDIR/.zshrc" ]]; then
    source "$R_CODE_USER_ZDOTDIR/.zshrc"
elif [[ -f "$HOME/.zshrc" ]]; then
    source "$HOME/.zshrc"
fi

_r_code_precmd() {
    local _exit_code=$?
    print -nP "\e]133;D;$_exit_code\a"
    print -nP "\e]133;A\a"
    print -nP "\e]133;B\a"
}

_r_code_preexec() {
    print -nP "\e]133;C\a"
}

precmd_functions=(_r_code_precmd $precmd_functions)
preexec_functions=(_r_code_preexec $preexec_functions)
"#;
    // ... 写入 .zshrc，设置 ZDOTDIR 环境变量
}
⚠️ 为什么不直接修改用户的配置文件？

R-Code 从不修改用户的 ~/.zshrc 或 ~/.bashrc。它会：

  1. 创建临时目录，写入自己的配置文件
  2. 在临时配置里 source 用户的原始配置
  3. 在原始配置的基础上添加 hooks

这样既保留了用户的所有自定义，又注入了 R-Code 需要的 OSC 133 支持。

6.7 外部 CLI Agent 检测

R-Code 需要检测终端里是否运行着外部 CLI Agent（如 claude 或 codex），因为这些 Agent 有自己独立的权限系统，不受 R-Code Tool Gateway 约束。

/// 检测进程是否为外部 CLI Agent（claude / codex）。
pub fn is_agent_process(process_name: &str) -> bool {
    let name = process_name.to_lowercase();
    name.contains("claude") || name.contains("codex")
}

当检测到 Agent 进程时，终端状态会切换到 Agent，R-Code 会在 UI 上显示警告，提示用户「当前终端里有不受 R-Code 管控的 Agent 在运行」。

🔴 为什么外部 CLI Agent 不受管控？

外部 CLI Agent（如 Claude Code、Codex CLI）直接与模型 API 通信，它们的工具调用走自己的权限系统。R-Code 的 Tool Gateway 只能管控通过自己工具注册表注册的工具。因此，当用户在 R-Code 终端里启动外部 CLI Agent 时，R-Code 无法阻止该 Agent 执行危险操作。

6.8 滚动缓冲区管理

每个终端都有一个 scrollback 缓冲区，用于存储历史输出。这个缓冲区有大小限制：

/// Scrollback 缓冲区最大大小（约 200KB）。
const MAX_SCROLLBACK: usize = 200_000;
📏 为什么是 200KB？

200KB 大约相当于 2000 行终端输出。对于大多数开发任务来说已经足够。如果无限增长，长时间运行的终端（比如日志 tail）会消耗大量内存。200KB 是一个兼顾「够用」和「不浪费内存」的折中值。

缓冲区截断策略

当新数据写入时，如果总大小超过 MAX_SCROLLBACK，会从缓冲区头部截断旧数据：

// 伪代码：滚动缓冲区截断
if scrollback.len() + new_data.len() > MAX_SCROLLBACK {
    let excess = scrollback.len() + new_data.len() - MAX_SCROLLBACK;
    scrollback.drain(0..excess);  // 从头部丢弃旧数据
}
scrollback.extend_from_slice(&new_data);

ANSI 转义序列处理

scrollback 缓冲区存储的是已剥离 ANSI 转义序列的纯文本。这意味着：

  • 颜色代码（\x1b[31m）被移除
  • 光标移动（\x1b[2J）被移除
  • OSC 133 标记被移除（因为它们属于 Shell Integration，不属于输出内容）

6.9 六个终端编排原语

TerminalManager 对外暴露了六个核心操作（编排原语），覆盖了终端的完整生命周期：

原语方法作用
createmanager.create(shell, dir, env)创建新终端
sendmanager.send(id, text)向终端 stdin 写入文本（模拟键盘输入）
writemanager.write(id, bytes)写入原始字节（用于特殊控制字符）
commandmanager.run_command(id, cmd)执行一条命令并等待结果
listmanager.list()列出所有终端
killmanager.kill(id)终止终端子进程

send vs write 的区别

send(text) → 普通文本输入 → 模拟用户打字
write(bytes) → 原始字节 → 发送 Ctrl+C、转义序列等

其他辅助方法

// 读取最新输出（drain 语义）
pub async fn read(&self, id: &TerminalId) -> Result<Vec<u8>, ProductError>

// 调整终端大小
pub async fn resize(&self, id: &TerminalId, cols: u16, rows: u16) -> Result<(), ProductError>

// 获取终端状态
pub async fn get_state(&self, id: &TerminalId) -> Result<TerminalState, ProductError>

6.10 与 Agent Worker 的集成

Agent 运行时（第 5 章）通过终端工具在终端里执行命令。这是一个关键的集成点：Agent 不直接调用 std::process::Command，而是通过 Tool Gateway 注册的终端工具来执行命令。

┌──────────────┐ │ Agent Loop │ │ │ │ ToolCall: │ │ "terminal. │ │ send" │ └──────┬───────┘ │ ▼ ┌──────────────┐ │ ToolGateway │ │ (权限检查) │ └──────┬───────┘ │ ▼ ┌──────────────┐ │TerminalManager│ │ send(id, │ │ command) │ └──────┬───────┘ │ ▼ ┌──────────────┐ │ PTY Master │ │ writer.write │ └──────┬───────┘ │ ▼ ┌──────────────┐ │ Shell 子进程 │ │ 执行命令 │ └──────┬───────┘ │ ▼ ┌──────────────┐ │ PTY Master │ │ reader.read │ └──────┬───────┘ │ ▼ ┌──────────────┐ │ scrollback │ │ + BlockParser│ └──────────────┘

背压处理

当命令输出很快时，后台读取线程会把数据推入 unbounded channel。如果消费端（前端或 Agent）来不及处理，channel 会无限增长。R-Code 通过以下方式处理背压：

  • unbounded channel —— 不会阻塞写入线程（PTY 输出不能丢）
  • scrollback 上限 —— 200KB 截断，防止内存无限增长
  • drain 语义的 read —— 每次 read 只取当前可用的数据，不积压

进程树管理

当 Agent 在终端里执行命令时，实际上创建了一个进程树：

shell (PTY 子进程) └── 命令进程 (如 npm test) └── 子进程 (如 jest) └── 孙进程 (如 node)

R-Code 需要跟踪前台进程，以便：

  • 判断终端是 Idle 还是 Busy
  • 在用户点击「停止」时正确终止命令（而不是只 kill shell）
  • 通过 OSC 133 D 标记准确判断命令何时结束
