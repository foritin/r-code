第 9 章：存储与持久化

R-Code 采用"双存储"架构：JSONL 作为不可变的事件真相源，SQLite 作为可查询的产品状态视图。本章带你理解数据如何安全落地。

9.1 双存储架构

R-Code 使用两套存储系统，各司其职：

hermes-store（JSONL）
不可变事件日志，Source of Truth
crash-safe：追加写入，不怕断电
用于审计、回放、崩溃恢复
r-code-store（SQLite）
产品状态视图，可查询
支持复杂查询、索引、事务
UI 直接读取的数据源
类比：会计账簿

JSONL 就像"流水账"——每一笔交易按时间顺序记录，永不修改。SQLite 就像"总账簿"——按科目分类汇总，方便查询。如果总账丢了，可以从流水账重新汇总。

9.2 数据流：事件先行

每次状态变化时，系统遵循"先写 JSONL，再投影到 SQLite"的顺序：

SessionEvent 发生 → 追加写入 JSONL → 投影到 SQLite → UI 更新
为什么先写 JSONL

JSONL 是追加写入，即使系统在"投影到 SQLite"之前崩溃，事件也不会丢失。重启后系统可以从 JSONL 重放（replay）所有事件，重建 SQLite 状态。

9.4 Database 结构体

Database 定义在 crates/r-code-store/src/database.rs，封装了 rusqlite + r2d2 连接池：

pub struct Database {
    pool: Pool<SqliteConnectionManager>,
}

impl Database {
    /// 打开文件数据库（WAL 模式 + foreign_keys ON）
    pub fn open(path: impl AsRef<Path>) -< Result<Self, ProductError> { ... }

    /// 打开内存数据库（用于测试）
    pub fn open_in_memory() -< Result<Self, ProductError> { ... }

    /// 获取连接（用于 repository 操作）
    pub fn conn() -< Result<PooledConnection, ProductError> { ... }
}
连接池大小

文件模式使用 max_size(8) 连接池，内存测试模式使用 max_size(1)。桌面应用低并发，WAL 模式支持多读单写。

9.5 WAL 模式与 PRAGMA

数据库打开时自动执行以下 PRAGMA 配置：

PRAGMA journal_mode=WAL;          -- 写前日志，支持并发读写
PRAGMA foreign_keys=ON;            -- 启用外键约束
PRAGMA synchronous=NORMAL;         -- 同步模式（性能与安全平衡）
PRAGMA busy_timeout=5000;          -- 锁等待超时 5 秒
PRAGMA值作用
journal_modeWALWrite-Ahead Logging，读写不互相阻塞
foreign_keysON保证引用完整性，防止孤儿记录
synchronousNORMALWAL 模式下足够安全，性能更好
busy_timeout5000ms等待锁释放，避免立即报错

9.6 Schema 迁移系统

R-Code 使用版本化迁移系统（定义在 crates/r-code-store/src/migrations.rs）：

pub fn run_migrations(conn: &Connection) -> Result<(), ProductError> {
    // 1. 创建 schema_version 表（如果不存在）
    conn.execute_batch(
        "CREATE TABLE IF NOT EXISTS schema_version (
            version INTEGER PRIMARY KEY,
            applied_at TEXT NOT NULL DEFAULT (datetime('now'))
        );"
    )?;

    // 2. 获取当前版本
    let current: i64 = conn.query_row(
        "SELECT COALESCE(MAX(version), 0) FROM schema_version", ...
    )?;

    // 3. 按序执行未应用的迁移
    let migrations: &[(i64, &str)] = &[(1, MIGRATION_001)];
    for (version, sql) in migrations {
        if *version > current {
            conn.execute_batch(sql)?;
            conn.execute("INSERT INTO schema_version (version) VALUES (?1)", ...)?;
        }
    }
}
幂等性保证

迁移可以安全地重复执行。已应用的迁移会被记录在 schema_version 表中，下次运行时会自动跳过。

9.7 BackupManager

BackupManager 定义在 crates/r-code-store/src/backup.rs，提供数据库备份与恢复功能：

pub struct BackupManager {
    backup_dir: PathBuf,
}

impl BackupManager {
    pub fn backup(&self, db_path: &Path) -> Result<PathBuf, ProductError>;
    pub fn restore(&self, backup_path: &Path, db_path: &Path) -> Result<(), ProductError>;
    pub fn list_backups(&self) -> Result<Vec<PathBuf>, ProductError>;
    pub fn verify(&self, backup_path: &Path) -> Result<bool, ProductError>;
}

备份命名规则

{db_stem}-{timestamp}.db
例如：r-code-20260725T143022.db

恢复流程

  1. 检查备份文件是否存在
  2. 清除目标位置的 -wal 和 -shm 边车文件
  3. 用备份文件覆盖目标数据库
  4. 下次打开时 SQLite 自动检查完整性
注意：WAL checkpoint

备份前应确保数据库连接已关闭或已 checkpoint。WAL 模式下，最后一个连接关闭时 SQLite 自动 checkpoint，主 .db 文件即为一致状态。

9.8 崩溃恢复流程

当 R-Code 异常退出后重启，系统执行以下恢复流程：

应用启动 → 打开 SQLite（WAL checkpoint） → 检查活跃 Run → 标记中断的 Run → 恢复完成

具体步骤：

  1. SQLite WAL 文件自动合并到主数据库（崩溃一致性由 WAL 保证）
  2. 查询 agent_runs 表中 ended_at IS NULL 的记录
  3. 将这些 Run 标记为异常终止（ended_at = 当前时间）
  4. 关联的 Task 状态根据情况回退到 Idle 或保持原状态
  5. 用户可以在 UI 中看到"上次会话被中断"的提示

9.9 Document Store

除了结构化数据，R-Code 还管理文档内容（如文件快照、验证输出等）。这些内容存储在 blob 存储中：

Blob 存储
内容寻址：以 SHA-256 哈希作为 key
引用计数：ref_count 跟踪使用方数量
自动清理：ref_count 归零时删除文件

Document Store 还维护 BOM（Bill of Materials）和 ConflictStatus：

  • BOM：记录一个 Task 涉及的所有文件及其哈希，用于完整性校验
  • ConflictStatus：标记文件是否存在合并冲突

9.11 会话截断修复

当会话历史过长时，系统会执行截断（truncation）以控制上下文大小。截断策略：

  • 保留任务目标、验收条件、计划状态
  • 保留未解决的权限请求和冲突
  • 保留当前变更摘要
  • 丢弃旧的详细工具调用日志
为什么需要截断

LLM 有上下文窗口限制。无限增长的会话会导致 token 溢出或成本飙升。截断确保只保留"决策相关信息"。
