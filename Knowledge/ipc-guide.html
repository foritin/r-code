一、什么是 IPC？

1.1 核心定义

IPC = Inter-Process Communication（进程间通信）

操作系统里，每个运行中的程序是一个进程。进程 A 和进程 B 默认是完全隔离的——A 看不到 B 的内存，B 也碰不到 A 的文件。但复杂软件经常需要多个进程配合工作，让两个独立进程互相传数据、互相调用，这就是 IPC。

1.2 生活比喻

现实场景IPC 对应
两个人在同一个房间说话共享内存（直接读写同一块数据）
两个人在不同城市打电话Socket（网络或本地 socket）
一个人给另一个人寄信管道（Pipe）/ 消息队列
公司里发邮件（写明收件人 + 附件）JSON-RPC over IPC（R-Code 的方案）
R-Code 选的是「寄邮件」的方式：进程之间用结构化的消息互相调用。每一封"邮件"都有明确的收件人（method）、内容（params）、编号（id），对方收到后回一封"回信"（response）。

二、为什么 R-Code 需要 IPC？

2.1 三进程架构

R-Code 有 三个进程，各司其职：

┌─────────────────────────────────────────────────────────────┐ │ Main 进程 (Tauri Rust 后端) │ │ ┌──────────────────────────────────────────────────────┐ │ │ │ 宿主服务层（管家） │ │ │ │ - Secret Store - Task Engine │ │ │ │ - Tool Gateway - Permission Engine │ │ │ │ - Change Service - Workspace Service │ │ │ │ - Document Service - Git Service │ │ │ │ - Search Service - Terminal Service │ │ │ │ - Verification Service │ │ │ └──────────────────────────────────────────────────────┘ │ │ ▲ │ │ IPC (Unix Socket / Named Pipe) │ │ ▼ │ │ ┌──────────────────────────────────────────────────────┐ │ │ │ Agent Worker 进程（独立进程 · 打工人） │ │ │ │ - Agent Runtime (Pi Adapter / Mock) │ │ │ │ - 无文件/命令执行器 │ │ │ │ - 无密钥存储 │ │ │ └──────────────────────────────────────────────────────┘ │ │ │ │ ┌──────────────────────────────────────────────────────┐ │ │ │ Renderer 进程（WebView · 前台小姐姐） │ │ │ │ - React + TypeScript UI │ │ │ │ - Monaco Editor │ │ │ │ - xterm.js 终端 │ │ │ └──────────────────────────────────────────────────────┘ │ └─────────────────────────────────────────────────────────────┘

2.2 为什么拆开三个进程？

设计目标解释
安全Agent Worker 直接面对 AI 模型（不可信输入），让它越权访问文件系统就炸了。单独一个进程，手里没有文件和命令执行器，只能「发消息请求 Main 帮忙执行」
隔离Renderer（WebView）崩了不能把整个 IDE 拖死
独立生命周期Worker 可以崩溃重启，不影响 UI 响应
拆开了之后，它们之间怎么对话？答案就是 IPC。没有 IPC，三进程就是三个孤岛，无法协作。

三、IPC 的「宽度」—— 所有通信方式一览

操作系统提供了多种 IPC 机制，各有适用场景：

方式原理典型用途R-Code 用吗？
管道 (Pipe)一根单向数据流，A 写 B 读终端 ls | grep foo❌
命名管道 (Named Pipe / FIFO)有名字的管道，不相关的进程也能用Windows 跨进程通信✅ Windows
Unix Socket本机 socket，用文件路径当地址macOS/Linux 本机进程通信✅ macOS
网络 Socket (TCP/UDP)走网络协议，可跨机器浏览器 ↔ 服务器❌
共享内存多进程映射同一块物理内存高频视频/图像处理（最快但最复杂）❌
消息队列内核维护的消息链表分布式系统削峰❌
D-BusLinux 桌面总线，桌面组件互相发现GNOME/KDE 桌面服务❌
COM / DCOMWindows 组件对象模型Office 插件、Windows 服务❌
R-Code 的选择：Unix Socket（macOS） + Named Pipe（Windows）。
为什么？因为这两者都是本机 socket 的变体——可以像网络编程一样收发消息，但数据不走网卡，本机内环回，既高性能又支持结构化协议。

四、R-Code IPC 的「深度」—— 四层协议栈

R-Code 的 IPC 不是简单传字符串，而是严格的四层结构：

第 4 层：应用语义  →  task.create / tool.execute / agent.event
↕
第 3 层：RPC 协议  →  JSON-RPC 2.0（请求/响应/事件）
↕
第 2 层：序列化帧  →  [4 字节长度][JSON 载荷]
↕
第 1 层：传输层  →  Unix Socket / Named Pipe

每一层只关心自己的事，这就是分层设计的魅力。下面逐层拆解。

第 1 层：传输层 —— 数据怎么流动？

macOS 方案：Unix Socket

// Main 进程：在 /tmp/charter.sock 这个路径上"挂牌营业"
use tokio::net::UnixListener;

let listener = UnixListener::bind("/tmp/charter.sock")?;
// Worker 进程：连上这个路径，Main 接受连接
let (stream, _addr) = listener.accept().await?;
你可以把 Unix Socket 想象成有一个固定门牌号的信箱。Main 进程把信箱放在 /tmp/charter.sock，Worker 和 Renderer 都知道这个地址，往里塞信、取信。

Windows 方案：Named Pipe

// 名字是 \\.\pipe\charter，Windows 内核管理
use tokio::net::windows::named_pipe::ServerOptions;

let pipe = ServerOptions::new().create(r"\\.\pipe\charter")?;
Windows 没有 Unix 那种「一切皆文件」的传统，所以用专门的「命名管道」——本质一样：一个内核维护的字节流通道，两端各拿一个句柄读写。

关键细节：启动时清理旧 socket

if socket_path.exists() {
    std::fs::remove_file(&socket_path)?;  // 上次崩溃留下的信箱得先拆掉
}

第 2 层：序列化帧 —— 怎么区分两条消息？

Socket 是字节流——水一样源源不断。你写了 3 个字节、再写 5 个字节，对面收到的是一摊 8 个字节的混合物。怎么知道「第一条消息在哪里结束」？

R-Code 的方案叫 length-prefixed framing：

[4 字节长度，大端 u32][N 字节 JSON 载荷] 发送 "hello"： [0x00 0x00 0x00 0x05] [h e l l o] ← 4 字节表示长度是 5 → ← 5 字节数据 →

接收方先读 4 字节 → 知道后面还有 5 字节 → 再读 5 字节 → 拼出一条完整消息。这是网络编程里最经典的拆包方式。

第 3 层：JSON-RPC 2.0 —— 消息长什么样？

数据拆出来了，接下来要知道它是什么意思。R-Code 用的是 JSON-RPC 2.0 协议——一种非常成熟的远程调用规范。

三种消息类型

(a) 请求（Request）：我要你帮我做件事，并且要结果

{
  "jsonrpc": "2.0",
  "id": "req-1",               // ← 唯一编号，用来匹配响应
  "method": "task.create",     // ← 要调用的方法名
  "params": {                  // ← 参数
    "goal": "Fix the bug"
  }
}

(b) 响应（Response）：你要的结果 / 失败原因

{
  "jsonrpc": "2.0",
  "id": "req-1",                       // ← 对应请求的 id
  "result": { "taskId": "task-123" }   // ← 成功时返回结果
}

或失败时：

{
  "jsonrpc": "2.0",
  "id": "req-1",
  "error": { "code": -32603, "message": "tool not found" }
}

(c) 事件（Notification）：单向通知，不要回复

{
  "jsonrpc": "2.0",
  "method": "agent.event",             // ← 没有 id
  "params": { "type": "message", "text": "Hello" }
}
这就像三种沟通方式：
• 请求 = 寄信等回信
• 响应 = 回信
• 事件 = 群发公告（不需要回复）

为什么用 JSON-RPC 而不是自己造协议？

  • 标准化：错误码、id 匹配、批量调用都有现成规范
  • 可读性：JSON 人能直接看懂，调试方便
  • 工具生态：可以自动生成 client/server 代码

第 4 层：应用语义 —— 具体在聊什么？

R-Code 的三对通信通道各有各的「业务」：

通道谁和谁传什么
Main ↔ Agent Worker管家 ↔ 打工人任务创建/恢复/中止、工具调用/结果、事件流
Main ↔ Renderer管家 ↔ 前台状态同步、UI 事件、投影数据
外部 CLI ↔ Main第三方 AI ↔ 管家终端控制（通过 Unix Socket + HTTP）
关键安全设计：Agent Worker 没有直接读文件的能力。它只能通过 IPC 跟 Main 说「帮我把这个文件读出来」，Main 读完再通过 IPC 把结果传回来。Worker 的一切 I/O 都要经过 Main 的权限检查。

五、服务端架构 —— Main 怎么处理请求？

struct IpcServer {
    listener: UnixListener,                           // 监听 socket
    handlers: HashMap<String, Box<dyn IpcHandler>>,   // method → 处理函数
}

impl IpcServer {
    // 每进来一个连接，开一个异步任务去处理（多并发不阻塞）
    pub async fn serve(&self) -> Result<()> {
        loop {
            let (mut stream, _addr) = self.listener.accept().await?;
            let handlers = self.handlers.clone();
            tokio::spawn(async move {
                if let Err(e) = Self::handle_connection(stream, handlers).await {
                    tracing::error!("IPC connection error: {}", e);
                }
            });
        }
    }
}

这是一个标准的 请求-分发-响应 模型：

连接进来
→
读取帧
→
解析 JSON
→
看 method
→
查 handlers 表
→
调用处理函数
→
写回响应
  • 每个 method（task.create、tool.execute、agent.event）注册一个 handler
  • 每进来一个连接，tokio::spawn 开一个异步任务去处理（多并发不阻塞）
  • 处理完一个连接上的所有请求后，该任务自动结束

六、安全层 —— 谁能连？能做什么？

维度机制
认证外部 CLI 用 per-terminal token；Renderer 用 session cookie
授权每个 IPC 调用检查权限，高风险操作需要审批
传输层安全Unix Socket 权限 0o600（仅 owner 可读写），别的用户进程连不上
数据校验JSON Schema 校验请求/响应，无效请求返回 ParseError
即使 Agent Worker 被模型输出操控了，它也只能发 IPC 请求。Main 收到后先检查权限——高风险操作弹出审批弹窗，用户不同意就拒绝执行。这就是 IPC 作为安全边界的价值。

八、Windows vs macOS 差异对比

维度macOSWindows
传输机制Unix SocketNamed Pipe
地址形式文件路径 /tmp/charter.sock名字 \\.\pipe\charter
权限控制文件权限 0o600（仅 owner）Windows ACL（访问控制列表）
代码标记#[cfg(unix)]#[cfg(windows)]
生命周期需手动清理残留 sock 文件Windows 内核自动清理
性能字节流，内核缓冲字节流，内核缓冲
协议层完全相同（JSON-RPC 2.0 + 序列化帧）
应用语义完全相同（task.create / tool.execute / agent.event）
关键洞察：传输层之上，协议层和应用层完全一致。这意味着业务代码不需要为两个平台各写一份——只有最底层的「连接建立」和「数据读写」需要条件编译。

9.2 关键概念速查

概念含义
进程运行中的程序实例，拥有独立的内存空间
Socket通信端点，像「网络插口」
Unix Socket本机 socket，用文件系统路径当地址，不走网卡
Named PipeWindows 上的等价物，用名字标识
JSON-RPC 2.0远程方法调用协议：请求带 id+method+params，响应带 id+result/error
length-prefixed frame[4 字节长度][载荷]，解决 TCP/流拆包问题
tokio::spawn开一个异步轻量任务，类似 goroutine
oneshot channel单次发送通道，请求方拿着 rx 等结果，响应方通过 tx 发一次
#[cfg(unix)]条件编译：仅在 Unix 系统（macOS）编译此代码
#[cfg(windows)]条件编译：仅在 Windows 编译此代码
