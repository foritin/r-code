第 5 章：Agent 运行时

Agent 运行时是 R-Code 的「大脑」——它负责与 AI 模型对话、调用工具、处理结果，并把整个过程变成前端可见的事件流。本章带你从 trait 定义到单次迭代、从崩溃恢复到测试替身，完整理解这个核心子系统。

5.1 什么是 Agent？

如果你刚接触「Agent」这个词，最容易的理解方式是这样的：

🧠 类比：AI 助手 = 一位新入职的实习生

想象你有一个很聪明的实习生（Agent）。你给他一个任务（比如「帮我把这个 bug 修了」），他会：

  • 读文件 —— 搞清楚代码现状
  • 思考 —— 决定怎么改
  • 改文件 —— 动手写代码
  • 跑命令 —— 验证改动是否正确
  • 汇报 —— 告诉你他做了什么

R-Code 的 Agent 运行时，就是管理这位实习生的「工位 + 工具箱 + 沟通系统」。

在代码层面，Agent 不是一个类或一个函数，而是一整套循环：

┌─────────────────────────────────────────────────────┐ │ Agent 循环 │ │ │ │ 用户输入 ──→ 模型 ──→ 工具调用 ──→ 结果 ──→ 模型 │ │ ↑ │ │ │ └────────────────────────────┘ │ └─────────────────────────────────────────────────────┘

这个循环会一直运行，直到模型认为任务完成（输出 StopReason::EndTurn），或者用户手动中止。每次「模型 → 工具 → 结果 → 模型」的往返，叫做一次迭代（iteration）。

5.2 Worker 进程的生命周期

R-Code 把 Agent 运行时放在一个独立进程（Worker）里。为什么要单独一个进程？

⚠️ 为什么 Agent 不能跑在 UI 进程里？
  1. 隔离崩溃 —— Agent 循环可能因为模型 bug 或工具死循环而卡住；单独进程崩溃不会拖垮整个 IDE。
  2. 资源隔离 —— 模型推理和工具执行可能消耗大量 CPU/内存；独立进程方便操作系统调度。
  3. 安全边界 —— Worker 没有直接访问文件系统的能力，所有文件操作必须通过 Tool Gateway 审批。

Worker 进程从启动到退出的完整生命周期：

① 启动 —— Electron Main 进程 fork/exec 启动 Worker
② 连接 —— Worker 与 Main 建立 IPC 通道（Unix Socket / Named Pipe）
③ 就绪 —— Worker 加载模型 provider，等待任务
④ 运行 —— 接收 session + goal，进入 agent 循环
⑤ 事件 —— 每次迭代产出事件，经 IPC 推送到 Main → Renderer
⑥ 结束 —— 任务完成或用户中止，Worker 退出或等待下一个任务

在第 3 章（IPC）里我们已经学到，Worker 和 Main 之间通过 JSON-RPC 2.0 通信。Agent 运行时在 Worker 内部运行，但对外暴露的接口就是 AgentRuntime trait。

5.3 AgentRuntime trait

AgentRuntime 是 R-Code 私有高层抽象，定义在 crates/r-code-agent-worker/src/runtime.rs。它把「与模型对话」和「调用工具」封装成一个统一的会话接口：

/// Agent Runtime -- R-Code 私有高层 trait。
#[async_trait]
pub trait AgentRuntime: Send + Sync {
    /// 创建新会话。
    async fn create_session(&mut self, input: CreateSessionInput) -> Result<Session, ProductError>;

    /// 启动一次 run -- 开始 agent 循环。返回 run id。
    async fn start_run(&mut self, session_id: &str, goal: &str) -> Result<String, ProductError>;

    /// Steer -- 在 run 中途注入用户消息。
    async fn steer(&mut self, session_id: &str, message: &str) -> Result<(), ProductError>;

    /// 中止当前 run。
    async fn abort(&mut self, session_id: &str) -> Result<(), ProductError>;

    /// 获取当前 run 的事件（drain 语义：取出后清空）。
    async fn poll_events(&mut self) -> Result<Vec<AgentEvent>, ProductError>;
}

五个方法各管一件事

方法作用类比
create_session创建一个新的对话上下文开一张新工单
start_run给 session 一个目标，开始干活给实习生布置任务
steer中途补充指令实习生干活时你补充说「顺便把这个也改了」
abort紧急停止喊「停！先别干了」
poll_events拉取最新进展（drain 语义）问实习生「进展如何？」然后清空待办
💡 为什么用 drain 语义？

poll_events 取出事件后会清空内部缓冲区。这保证了每个事件只被消费一次，避免了「前端拉取同一批事件两次」的问题。前端只需要定期（比如每 50ms）调用一次 poll_events，就能拿到 Agent 的最新产出。

5.4 Agent Loop 单次迭代详解

Agent 循环的核心实现在 crates/r-code-agent-worker/src/agent_loop.rs。函数签名如下：

pub async fn run_agent_loop_iteration(
    provider: &dyn LlmProvider,
    tool_host: &dyn ToolHost,
    mut request: CompletionRequest,
    messages: &mut Vec<Message>,
    tools: &[ToolSpec],
) -> Result<Vec<AgentEvent>, ProductError>

一次迭代做的事情，可以用六步来概括：

┌──────────────────────────────────────────────────────────────┐ │ Agent Loop 单次迭代 │ │ │ │ ① provider.stream(request) │ │ │ │ │ ▼ │ │ ② TextDelta ──→ 累积文本 + emit Message 事件 │ │ │ │ │ ▼ │ │ ③ ToolUseStart/Delta ──→ 跟踪工具调用 + 累积 input JSON │ │ │ │ │ ▼ │ │ ④ ToolUseComplete ──→ tool_host.call() + emit ToolCall │ │ │ + emit ToolResult │ │ ▼ │ │ ⑤ Stop ──→ 结束本次迭代 │ │ │ │ │ ▼ │ │ ⑥ 追加 assistant 消息 + 可选 user 消息（tool_result） │ └──────────────────────────────────────────────────────────────┘

步骤 ①：调用模型获取事件流

request.messages = messages.clone();
request.tools = tools.to_vec();

let mut stream = provider.stream(request).await.map_err(map_hermes_err)?;

把当前对话历史（messages）和可用工具列表（tools）塞进请求，然后调用模型的流式接口。provider.stream() 返回一个异步流（Stream），模型会源源不断地往里面塞事件。

步骤 ②：处理 TextDelta

StreamEvent::TextDelta { text } => {
    current_text.push_str(&text);
    events.push(AgentEvent::Message { text, delta: true });
}

模型一边生成文本，一边以 TextDelta 的形式流式输出。Agent 循环做两件事：

  1. 把文本片段拼接到 current_text（最终会成为 assistant 消息的正文）。
  2. 把每个 delta 包装成 AgentEvent::Message 推送给前端——这就是你在 UI 上看到「模型正在打字」的效果。

步骤 ③④：跟踪工具调用

当模型决定调用一个工具时，会先发 ToolUseStart（告诉你「我要用工具 X 了」），然后发一串 ToolUseDelta（工具的输入 JSON 片段），最后发 ToolUseComplete（输入完整了）。

StreamEvent::ToolUseStart { id, name } => {
    flush_text(&mut current_text, &mut assistant_blocks);
    pending_tools.insert(id, (name, String::new()));
}
StreamEvent::ToolUseDelta { id, input_json } => {
    if let Some((_, acc)) = pending_tools.get_mut(&id) {
        acc.push_str(&input_json);
    }
}

当 ToolUseComplete 到来时，真正执行工具：

StreamEvent::ToolUseComplete { id, input } => {
    flush_text(&mut current_text, &mut assistant_blocks);
    let name = pending_tools.remove(&id).map(|(n, _)| n).unwrap_or_default();
    // 追加 ToolUse 块到 assistant 消息
    assistant_blocks.push(ContentBlock::ToolUse { id, name: name.clone(), input: input.clone() });
    // emit ToolCall 事件
    events.push(AgentEvent::ToolCall { name, input, call_id: id.clone() });
    // 调用工具主机
    let outcome = tool_host.call(&name, input).await.map_err(map_hermes_err)?;
    // emit ToolResult 事件
    events.push(AgentEvent::ToolResult { call_id: id, output, is_error });
}
🔧 flush_text 是什么？

当工具调用开始时，之前累积的 current_text 需要被「冲刷」成一个 ContentBlock::Text 放进 assistant_blocks。这保证了 assistant 消息的正文在工具调用之前结束，不会混在一起。

步骤 ⑤⑥：结束迭代 & 组装消息

// 追加 assistant 消息（含 Text + ToolUse 块）
if !assistant_blocks.is_empty() {
    messages.push(Message {
        role: Role::Assistant,
        content: std::mem::take(&mut assistant_blocks),
        ..Default::default()
    });
}

// 如果因工具调用停止，追加 user 消息（含 ToolResult 块）
if stop_reason == StopReason::ToolUse && !tool_results.is_empty() {
    messages.push(Message {
        role: Role::User,
        content: std::mem::take(&mut tool_results),
        ..Default::default()
    });
}

注意 StopReason::ToolUse 的处理：当模型因为调用工具而停止时，工具结果会被包装成 user 消息追加到对话历史。这样下一次迭代时，模型就能看到工具的返回结果，决定下一步动作。

5.5 LLM 抽象层

R-Code 使用 hermes-llm 提供的 LlmProvider trait 作为模型抽象层。这个 trait 定义了Agent 与 LLM 交互的标准接口，R-Code 的 Agent Worker 代码只依赖这个抽象 trait，不直接依赖任何具体的模型 SDK。

Agent Loop → LlmProvider trait → 具体实现 → 模型 API
📐 为什么使用抽象 trait？

LlmProvider 是 hermes-llm 定义的接口（类似于「插座标准」），具体的模型后端（如 Anthropic、OpenAI 等）提供各自的实现。这种设计让我们可以：

  • 随时切换到另一个模型提供商（只需换一个 LlmProvider 实现）
  • 在测试时注入 MockAgentRuntime（不需要真实模型）
  • 让 Agent 循环不依赖具体的模型 SDK，只依赖抽象 trait
⚠️ 路径 B：不使用 Pi SDK

R-Code 不依赖 Pi SDK。deny.toml 中明确禁止 pi-sdk、pi-sdk-core、pi-sdk-agent、pi-agent 相关依赖。R-Code 直接基于 hermes-llm 的 LlmProvider trait 实现 agent 循环（称为「路径 B」），而非使用 Pi SDK 提供的现成 Agent 运行时。

5.6 事件流与 StreamEvent 类型

Agent 循环消费的是 StreamEvent（来自 hermes-llm），产出的是 AgentEvent（R-Code 自有 DTO）。两者是一对一映射关系：

StreamEvent（输入）→AgentEvent（输出）
TextDelta→AgentEvent::Message { delta: true }
ToolUseStart + Delta + Complete→AgentEvent::ToolCall + AgentEvent::ToolResult
Stop→结束本次迭代（无事件）
Usage→累加 token 用量（内部统计）

这种映射让 Agent 循环成了一个「黑盒」：外部只看到 AgentEvent 流，不需要关心模型内部是怎么流式输出的。

5.7 工具调用回路（ToolHost trait）

ToolHost 是 hermes-llm 定义的工具执行接口。R-Code 的 ToolGateway 实现了这个 trait，把工具调用接入权限检查、审计记账等安全机制（详见第 7 章）。

// ToolHost trait（hermes-llm 定义）
#[async_trait]
pub trait ToolHost: Send + Sync {
    async fn call(&self, name: &str, input: serde_json::Value) -> Result<ToolCallOutcome, Error>;
    async fn list_tools(&self) -> Result<Vec<ToolSpec>, Error>;
}

// ToolGateway 实现 ToolHost（r-code-gateway）
#[async_trait]
impl ToolHost for ToolGateway {
    async fn call(&self, name: &str, input: serde_json::Value) -> Result<ToolCallOutcome, Error> {
        // 权限检查 + 执行 + 记账
        self.execute_call(task_id, run_id, name, input, caller).await
            .map_err(|e| Error::ToolHost(e.to_string()))
    }
}

工具调用的完整回路：

模型 ──ToolUseComplete──→ agent_loop ──tool_host.call()──→ ToolGateway │ ┌───────────────┤ ▼ ▼ 权限检查 工具注册表 │ │ ▼ ▼ 审批/拒绝 执行工具.execute() │ ▼ ToolResult ←── ToolCallOutcome

5.8 崩溃恢复：scan_orphaned_runs

Worker 进程可能因为各种原因崩溃（OOM、段错误、被系统杀掉）。崩溃时，可能有一些 run 还在执行中，数据库里留下 ended_at IS NULL 的记录——这些就是孤儿 run。

//! 崩溃恢复 -- 扫描中断的 agent run。
//!
//! Worker 崩溃后，可能留下 `ended_at IS NULL` 的 agent run 记录。
//! 本模块负责扫描这些孤儿 run，供上层决定恢复 / 标记失败 / 重新调度。

pub struct RecoveryState {
    pub task_id: String,
    pub session_id: String,
    pub last_state: TaskState,
    pub interrupted: bool,
}

pub fn scan_orphaned_runs() -> Vec<RecoveryState> {
    // 当前为桩实现，存储层接入后补全
    Vec::new()
}
⚠️ 当前状态：桩实现

scan_orphaned_runs 目前返回空列表。完整的实现需要查询数据库中 ended_at IS NULL 的 agent run 记录，然后根据 last_state 决定是恢复执行还是标记为失败。这是 R4 阶段的待办事项。

恢复策略的三种可能

场景恢复策略
run 在「探索阶段」崩溃可以安全重跑（没有副作用）
run 在「执行阶段」崩溃（已修改文件）需要回滚到上一个 checkpoint，再决定
run 在「审批等待」崩溃清除 pending 请求，通知用户

5.9 MockAgentRuntime（测试用）

在集成测试中，我们不想真的调用 AI 模型。MockAgentRuntime 就是为此设计的测试替身：

// MockAgentRuntime 允许测试注入预设的「模型响应」
let mut runtime = MockAgentRuntime::new();
runtime.push_text_turn("Let me check that", Usage::new(3, 4));
provider.push_turn(RecordedTurn::ok(vec![
    StreamEvent::TextDelta { text: "Let me check ".to_string() },
    StreamEvent::TextDelta { text: "that".to_string() },
    StreamEvent::Usage(Usage::new(5, 5)),
    StreamEvent::Stop { reason: StopReason::EndTurn },
]));

Mock 的核心思想：

  • 预设响应：测试可以提前压入（push）一系列「模型会返回什么」。
  • 确定性：同样的输入永远得到同样的输出，方便断言。
  • 无需网络：不调用真实的模型 API，测试可以在 CI 中快速运行。
✅ 测试示例
#[tokio::test]
async fn tool_use_delta_accumulates_input() {
    let provider = MockProvider::new("mock");
    provider.push_turn(RecordedTurn::ok(vec![
        StreamEvent::ToolUseStart { id: "t1".to_string(), name: "echo".to_string() },
        StreamEvent::ToolUseDelta { id: "t1".to_string(), input_json: "{\"a\":".to_string() },
        StreamEvent::ToolUseDelta { id: "t1".to_string(), input_json: "1}".to_string() },
        StreamEvent::ToolUseComplete { id: "t1".to_string(), input: serde_json::json!({"a": 1}) },
        StreamEvent::Stop { reason: StopReason::ToolUse },
    ]));
    // 断言 ToolCall 携带完整 input
    let call = events.iter().find_map(|e| match e {
        AgentEvent::ToolCall { input, .. } => Some(input.clone()),
        _ => None,
    });
    assert_eq!(call, Some(serde_json::json!({"a": 1})));
}

5.10 Agent 事件类型

Agent 运行时对外暴露的事件类型是 AgentEvent，定义在 r-code-core/src/dto.rs：

pub enum AgentEvent {
    /// 文本消息（增量 delta 或完整）
    Message {
        text: String,
        delta: bool,          // true = 增量片段，false = 完整消息
    },
    /// 工具调用
    ToolCall {
        name: String,         // 工具名称
        input: serde_json::Value, // 输入参数
        call_id: String,      // 调用 ID（用于关联 ToolResult）
    },
    /// 工具结果
    ToolResult {
        call_id: String,      // 对应的 ToolCall ID
        output: serde_json::Value, // 输出结果
        is_error: bool,       // 是否执行出错
    },
    /// Agent 计划
    Plan {
        steps: Vec<PlanStep>,
    },
}

前端通过消费这些事件来更新 UI：

事件前端行为
AgentEvent::Message { delta: true }在对话流中追加文本片段（打字机效果）
AgentEvent::ToolCall显示「正在调用工具 X」的进度卡片
AgentEvent::ToolResult展示工具输出；如果是错误则高亮红色
AgentEvent::Plan渲染 Agent 的计划步骤列表

5.11 本章小结

本章我们从「什么是 Agent」出发，一步步拆解了 Agent 运行时的核心机制：

┌─────────────────────────────────────────────────────────────┐ │ Agent 运行时全景图 │ │ │ │ ┌──────────┐ ┌──────────┐ ┌──────────┐ │ │ │ 前端 UI │◄───│ IPC 通道 │◄───│ Main │ │ │ └──────────┘ └──────────┘ └────┬─────┘ │ │ │ fork │ │ ▼ │ │ ┌──────────────┐ │ │ │ Worker │ │ │ │ │ │ │ │ AgentRuntime │ │ │ │ trait impl │ │ │ │ │ │ │ │ │ ▼ │ │ │ │ Agent Loop │ │ │ │ │ │ │ │ │ ┌───┴───┐ │ │ │ │ ▼ ▼ │ │ │ │Model ToolHost│ │ │ │Adapter │ │ │ │ │ │ ▼ │ │ │ │ │ ToolGateway│ │ │ │ │ (权限+审计) │ │ │ └──────────────┘ │ └─────────────────────────────────────────────────────────────┘
  • Agent 是一个循环：模型 → 工具 → 结果 → 模型，直到任务完成。
  • AgentRuntime trait 提供了 create_session / start_run / steer / abort / poll_events 五个方法。
  • Agent Loop 每次迭代：获取流式事件 → 累积文本 → 跟踪工具调用 → 执行工具 → 组装消息。
  • ToolHost 是工具执行的抽象接口，ToolGateway 提供带权限检查的实现。
  • 崩溃恢复 通过 scan_orphaned_runs 扫描孤儿 run（当前是桩实现）。
  • MockAgentRuntime 让测试可以在不调用真实模型的情况下运行。
