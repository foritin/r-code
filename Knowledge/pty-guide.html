一、什么是 PTY？—— 先从「终端」说起

1.1 远古时代：真正的物理终端

上世纪 70 年代，计算机是一台昂贵的大铁柜。用户要跟它交互，得用一种叫 终端（Terminal） 的物理设备——一个屏幕 + 键盘，用一根串口线连到主机。经典的 VT100、DECWriter 都是这类东西。

┌──────────────┐ 串口线 ┌──────────────────┐ │ 物理终端 │ ◄──────────► │ 大型主机 │ │ (VT100) │ │ (运行程序) │ │ 屏幕+键盘 │ │ │ └──────────────┘ └──────────────────┘

终端负责：接收键盘输入 → 发给主机 → 接收主机输出 → 显示在屏幕上。

1.2 问题来了：软件怎么假装自己是终端？

后来图形界面（macOS、Windows）普及了，物理终端消失了。但有一个问题：大量软件（shell、vim、htop、ssh）默认自己只认「终端」——它们会调 isatty() 检查「我是不是连在一个终端上」，如果不是，就拒绝交互、拒绝彩色输出。

比如 ls 在管道里就不输出彩色：

$ ls --color=auto          # 直接运行 → 有颜色（因为 stdout 是终端）
$ ls --color=auto | cat    # 管道 → 没颜色（因为 stdout 是管道，不是终端）

能不能「假装」给程序连了一个终端，实际上是我的 UI 在背后控制？

这就是 PTY（Pseudo-Terminal，伪终端）。

1.3 一句话定义

PTY = 伪终端：操作系统内核提供的一对「假的」终端设备。你（IDE/终端模拟器）拿着一端假装成「屏幕+键盘」，另一端连着程序（shell）。程序以为自己在跟真正的终端对话，实际上完全在你的掌控之中。

二、生活比喻 —— 给秘书配了一个「假前台」

想象一家大公司：

  • 秘书（Shell）：只能跟「前台」打交道。你直接走进去找她，她不理你。
  • 前台（PTY Slave）：秘书只认前台。有访客来，前台接待；有电话来，前台接听。
  • 经理（你的 IDE）：坐在里间控制一切。经理面前有一个对讲机（PTY Master），能听到前台听到的一切，也能通过对讲机对前台说话。
┌────────────────────────────────────────────┐ │ 经理的办公室 (IDE) │ │ ┌──────────────┐ │ │ │ 对讲机 (Master)│ ◄── 经理通过对讲机 │ │ └──────┬───────┘ 听到/对前台说话 │ │ │ 内线 │ │ ┌──────┴───────┐ │ │ │ 前台 (Slave) │ ◄── 秘书只认前台 │ │ └──────┬───────┘ │ │ │ 面对面 │ │ ┌──────┴───────┐ │ │ │ 秘书 (Shell) │ ◄── 普通程序 │ │ └──────────────┘ │ └────────────────────────────────────────────┘

秘书以为自己在正常上班，实际上前台的一举一动都被经理通过对讲机监听了。经理可以：

  • 录下前台和秘书的所有对话（捕获输出）
  • 通过对讲机替访客传话（发送键盘输入）
  • 告诉前台「窗户尺寸变了」（发送 SIGWINCH 信号调整窗口大小）
  • 随时切断通话（kill 子进程）

三、PTY 的「宽度」—— 前世今生与两种实现

3.1 历史演进

年代名称特点
1980sUnix BSD PTY/dev/ptyXX + /dev/ttyXX，需要预先分配固定数量
1990sUnix Unix98 PTY一次 API 分配，不再需要预分配，/dev/ptmx
2000sUnix devpts内核自动管理 pts 设备，fork+exec 即用
2018Windows ConPTYWindows 10 1809 引入，终于有了「真正的」PTY 支持

3.2 两种主流实现

Unix/macOS：Master-Slave 对

// 打开一对 PTY
master_fd = open("/dev/ptmx", O_RDWR);  // Master：控制端
grantpt(master_fd);                      // 授权
unlockpt(master_fd);                     // 解锁
slave_name = ptsname(master_fd);         // 获取 Slave 路径

// fork 子进程，子进程连上 Slave
if (fork() == 0) {
    close(master_fd);
    fd = open(slave_name, O_RDWR);       // Slave：被控制端
    dup2(fd, 0); dup2(fd, 1); dup2(fd, 2);  // stdin/stdout/stderr
    execvp("bash", ...);                 // Shell 连上了伪终端！
}

Windows：ConPTY（Console Pseudoterminal）

// Windows ConPTY API（简化）
CreatePseudoConsole(size, hPipeIn, hPipeOut, 0, &hPC);
// hPipeIn/hPipeOut 是 Windows Pipe，连接 Master 端
// 子进程用 hPC 作为 Console 启动
历史趣闻：Windows 在 2018 年之前没有 PTY 概念！所有终端程序（ssh、vim）在 Windows 上要么靠 Cygwin/MSYS2 模拟，要么靠 winpty 等 hack 方案。这也是为什么 Windows Terminal 和 VS Code 终端过去那么折腾。ConPTY 的引入（Windows 10 1809）彻底改变了这一状况。

3.3 PTY 与相关概念对比

概念区别能否跑交互式程序
管道 (Pipe)单向字节流，无终端语义❌ 程序检测到非终端就拒绝交互
PTY双向 + 终端语义 + 信号✅ 程序完全无感知
TTYTeletypewriter，终端的统称是 PTY 的父概念
Shell命令解释器，不是终端需要跑在 PTY/TTY 之上
ConsoleWindows 的终端系统Windows 等价物

四、PTY 的「深度」—— Master / Slave 工作原理

4.1 完整架构图

┌──────────────────────────────────────────────────────────────────────┐ │ 你的程序 (IDE / 终端模拟器) │ │ │ │ ┌─────────────┐ 读写 ┌──────────────────────────────────────┐ │ │ │ 应用逻辑 │◄─────►│ Master 端 (/dev/ptmx 或 ConPTY) │ │ │ │ - 渲染屏幕 │ │ - 发送键盘输入 │ │ │ │ - 捕获输出 │ │ - 接收程序输出 │ │ │ │ - 调整大小 │ │ - 发送窗口大小变化 (SIGWINCH) │ │ │ └─────────────┘ └───────────────┬──────────────────────┘ │ │ │ │ │ ┌────────────────────┼────────────────────┐ │ │ │ 内核 (Line Discipline + PTY 驱动) │ │ │ │ - 处理回显、行编辑、Ctrl+C │ │ │ │ - 转换 \n ↔ \r\n │ │ │ └────────────────────┼────────────────────┘ │ │ │ │ │ ┌─────────────┐ 读写 ┌───────────────┴──────────────────────┐ │ │ │ Shell/程序 │◄─────►│ Slave 端 (/dev/pts/N 或 ConPTY) │ │ │ │ (bash/zsh) │ │ - 程序的 stdin/stdout/stderr │ │ │ │ 以为这是 │ │ - 程序 isatty() → true │ │ │ │ 真终端！ │ │ - 可以跑 vim、htop、ssh 等 │ │ │ └─────────────┘ └──────────────────────────────────────┘ │ └──────────────────────────────────────────────────────────────────────┘

4.2 数据流向

方向数据路径
键盘 → Shell按键字节IDE 写入 Master → 内核 Line Discipline → Slave → Shell stdin
Shell → 屏幕输出字节（含 ANSI 转义序列）Shell stdout → Slave → 内核 Line Discipline → Master → IDE 读取
窗口大小变化SIGWINCH 信号IDE 调用 resize() → 内核更新 winsize → 发 SIGWINCH 给 Shell
Ctrl+CSIGINT 信号IDE 写入 0x03 字节 → 内核 Line Discipline 拦截 → 发 SIGINT 给 Shell

4.3 Line Discipline（线路规程）—— PTY 的灵魂

Master 和 Slave 之间不是直连的，中间有一个 Line Discipline（线路规程）——内核里的一个「中间人」，负责：

  • 回显（Echo）：你按的字符是否显示在屏幕上（密码输入时要关掉）
  • 行编辑（Line Editing）：Backspace 删除、Ctrl+U 清空行
  • 字符转换：输出时 \n → \r\n；输入时 \r → \n
  • 信号生成：收到 Ctrl+C → 转换为 SIGINT 发给子进程
  • EOF：收到 Ctrl+D → 子进程读到 EOF
没有 Line Discipline，Master 和 Slave 之间就是原始的字节流。Line Discipline 的存在，使得 Slave 端连上的程序「以为」自己连了真正的终端。

4.4 窗口大小（Winsize）与 SIGWINCH

// 告诉内核：终端窗口大小变了
ioctl(master_fd, TIOCSWINSZ, &winsize);
// 内核随即向子进程发送 SIGWINCH 信号
// Shell 收到后调用 ioctl(TIOCGWINSZ) 读取新尺寸，更新 $LINES/$COLUMNS

这就是为什么你拖拽终端窗口大小时，vim、htop 能立刻知道新尺寸——PTY 机制自动完成了这一切。

4.5 一对 PTY 能连几个 Slave？

一个 Master 只能连一个 Slave。每个 PTY 对应一个独立的终端会话。这就是为什么 IDE 开多个终端标签需要创建多个 PTY 实例。

五、为什么需要 PTY？—— 不用 PTY 会怎样？

5.1 对比表

场景用 Pipe用 PTY
ls | grep foo✅ 够用✅ 也可以
跑 vim❌ vim 拒绝启动（"Output is not a terminal"）✅ vim 正常启动
跑 ssh❌ ssh 无法处理密码输入（关掉回显）✅ 正常交互
Shell 提示符着色❌ ls 不输出彩色✅ 完整彩色输出
调整窗口大小❌ 程序不知道窗口大小✅ SIGWINCH 自动通知
Ctrl+C 中断❌ 需要自行处理✅ 内核自动发 SIGINT

5.2 核心原因

大量命令行程序默认自己是跟「人」直接打交道的。它们会调用 isatty(fd) 检查 stdin/stdout 是否是 TTY 设备：

  • 如果是 TTY → 彩色输出、逐行缓冲、支持交互式编辑
  • 如果不是 TTY → 无颜色、全缓冲、拒绝交互
不用 PTY 的后果：你的 IDE 终端里跑不了 vim、htop、ssh、top、less 等任何交互式程序。Shell 的提示符也不会有颜色。这就是为什么终端模拟器（iTerm2、Windows Terminal、VS Code 终端）底层都必须用 PTY。

6.2 portable-pty crate

R-Code 使用 portable-pty 这个 Rust crate 来跨平台管理 PTY。它的核心 API：

use portable_pty::{
    native_pty_system, Child, CommandBuilder, MasterPty, PtyPair, PtySize, PtySystem,
};

// 1. 获取当前系统的 PTY 实现
let pty_system = native_pty_system();

// 2. 打开一对 PTY（返回 Master + Slave）
let pair = pty_system.openpty(PtySize {
    rows: 24, cols: 80, pixel_width: 0, pixel_height: 0,
})?;

// 3. 在 Slave 端启动 Shell
let cmd = CommandBuilder::new("/bin/zsh");
let child = pair.slave.spawn_command(cmd)?;

// 4. 从 Master 读取 Shell 输出
let mut reader = pair.master.try_clone_reader()?;

// 5. 向 Master 写入键盘输入（Shell 会收到）
let mut writer = pair.master.take_writer()?;
writer.write_all("ls -l\r\n".as_bytes())?;

6.3 R-Code 的 TerminalHandle 结构

pub struct TerminalHandle {
    pub id: TerminalId,
    pub state: TerminalState,       // Idle / Busy / Agent / Exited
    pub shell: String,              // "zsh" / "bash" / "fish"
    pub working_dir: PathBuf,
    pub scrollback: Vec<u8>,        // 输出缓冲（约 200KB）
    child: Box<dyn Child>,         // PTY 子进程
    writer: Box<dyn Write>,        // PTY stdin 写入器
    master: Box<dyn MasterPty>,    // PTY master（resize + reader）
    output_rx: mpsc::UnboundedReceiver<Vec<u8>>,  // 后台读取线程
    killed: bool,                   // 防止重复 kill
}

6.4 多终端管理

R-Code 的 TerminalManager 管理多个终端实例：

pub struct TerminalManager {
    pty_system: Box<dyn PtySystem>,
    terminals: Arc<Mutex<HashMap<TerminalId, TerminalHandle>>>,
    // 每个终端 = 一个独立的 PTY + Shell 子进程
}

每个终端标签对应一个 TerminalHandle，拥有独立的：

  • PTY Master-Slave 对
  • Shell 子进程（zsh/bash/fish）
  • Scrollback 缓冲区（约 200KB 上限）
  • 后台读取线程（持续从 Master 读输出）

七、块模型与 OSC 133 —— 从终端输出中挖结构化数据

7.1 问题：终端输出是「一锅粥」

终端输出是连续的字节流，混合了：

  • Shell 提示符
  • 命令文本
  • 程序输出（含 ANSI 颜色代码）
  • 退出码信息

IDE 怎么知道「哪段输出属于哪条命令」？

7.2 解决方案：OSC 133 Shell Integration

Shell（zsh/bash/fish）在每条命令执行前后注入特殊的 OSC 133 转义序列，像「书签」一样标记命令边界：

命令开始 (prompt) 命令文本 命令结束 (输出) 退出码 │ │ │ │ ▼ ▼ ▼ ▼ OSC 133 A OSC 133 B OSC 133 C OSC 133 D (标记开始) (命令开始) (输出开始) (退出码=N)
OSC 序列含义时机
OSC 133 A ST命令开始（prompt 结束）Shell 显示提示符后
OSC 133 B ST命令文本开始用户按下 Enter 后
OSC 133 C ST输出开始命令开始执行
OSC 133 D;exit ST命令结束（含退出码）命令执行完毕

7.3 块类型

R-Code 解析 OSC 133 序列，将终端输出切分为两种「块」：

块类型含义包含内容
Command一条 shell 命令prompt → command line → output → exit code
Turn外部 Agent 会话边界claude/codex 的一次完整交互

7.4 块位置用 xterm Marker 存储

块的起止位置用 xterm.js 的 Marker 标记，自然存活于滚动缓冲区。即使输出被滚走，Marker 仍然记得「第 42 行到第 100 行是某条命令的输出」。

7.5 命令文本读取

从 buffer 的 B marker（记录 cursor column）到 C 时的 cursor 位置，就是用户输入的命令文本。不需要私有转义序列，兼容任何已有 OSC 133 集成。

维度macOS (Unix PTY)Windows (ConPTY)

好消息：portable-pty crate 已经帮你抹平了这些差异。R-Code 的业务代码只需要跟 MasterPty / Child / PtySystem 这些 trait 打交道，不需要关心底层是 Unix PTY 还是 ConPTY。

9.3 与 IPC 的关系

PTY 和 IPC 是 R-Code 中不同层面的通信机制：

机制连接什么传输什么
PTYMain ↔ Shell/外部程序终端字节流（键盘输入 + 程序输出）
IPCMain ↔ Agent Worker / Renderer结构化 JSON-RPC 消息
一句话：PTY 让 Main 能「控制」Shell（像人用终端一样），IPC 让 Main 能「指挥」其他进程（像老板发邮件一样）。两者配合，R-Code 既能跑交互式命令行，又能让 Agent 通过结构化消息编排一切。
