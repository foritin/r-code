第 4 章：PTY 伪终端

IDE 里的终端窗口是怎么"骗过" Shell 让它以为自己在跟真人交互？这一章我们拆解 PTY（Pseudo-Terminal，伪终端）的完整机制——从电传打字机的历史到 R-Code 如何管理多个终端实例。

一、什么是终端？—— 从电传打字机说起

要理解 PTY，得先理解"终端"是什么。让我们回到 1960 年代：

┌──────────────────────────────────────────────────────────────────────┐ │ 1960 年代的大型机时代 │ │ │ │ ┌─────────────┐ ┌──────────────────┐ │ │ │ 电传打字机 │ ◄────── 串行线缆 ──────► │ 大型计算机 │ │ │ │ (TTY) │ │ (Mainframe) │ │ │ │ - 键盘 │ │ │ │ │ │ - 打印机 │ │ │ │ │ └─────────────┘ └──────────────────┘ │ │ │ │ 用户敲键盘 → 字符通过线缆传到大型机 → 大型机处理 → 结果传回打字机打印 │ └──────────────────────────────────────────────────────────────────────┘

那时候的"终端"是一个真实的物理设备——一台电传打字机（Teletypewriter，缩写 TTY）。它通过串行线缆连接到大型计算机，负责输入和输出。

终端的演进

年代设备特点
1960s电传打字机（TTY）物理设备，键盘 + 打印机
1970sCRT 终端（VT100）屏幕代替打印机，支持光标移动
1990s终端模拟器（xterm）软件模拟终端，跑在图形界面里
现在IDE 内置终端VS Code、R-Code 等 IDE 内置的终端面板
💡 核心概念
终端（Terminal）本质上是人机交互的入口——你通过它输入命令，它显示结果。现代终端是软件模拟的，但程序（比如 Shell）仍然以为自己在跟"真正的终端"对话。这就是 PTY 存在的意义。

二、什么是 PTY？—— 分机电话

PTY = Pseudo-Terminal（伪终端）。所谓"伪"，就是"假的"——它不是真正的物理终端，而是内核提供的一对假的终端设备。

类比：分机电话

┌──────────────────────────────────────────────────────────────────────┐ │ 类比：公司里的分机电话 │ │ │ │ ┌─────────────┐ ┌─────────────┐ ┌─────────────┐ │ │ │ 前台总机 │ ◄────► │ 电话交换机 │ ◄────► │ 员工分机 │ │ │ │ (Master) │ │ (内核) │ │ (Slave) │ │ │ │ │ │ │ │ │ │ │ │ IDE 持有 │ │ 转发声音 │ │ Shell 持有 │ │ │ │ 负责拨号 │ │ 处理信号 │ │ 以为是真的 │ │ │ └─────────────┘ └─────────────┘ └─────────────┘ │ │ │ │ 前台拨分机 → 交换机转发 → 员工接听（以为直接跟前台通话） │ └──────────────────────────────────────────────────────────────────────┘

PTY 由一对设备组成：

端谁持有职责类比
MasterIDE / 终端模拟器读写数据、控制终端前台总机
SlaveShell / 子程序程序的 stdin/stdout/stderr员工分机
✅ 关键洞察
Slave 端的程序（比如 bash、vim、ssh）完全不知道自己连的是"假的"终端。它调用 isatty() 检查会返回 true，一切行为都和连了真终端一样。这就是 PTY 的魔力。

三、为什么需要 PTY？—— 不用 PTY 会怎样？

你可能会想：我直接用管道（Pipe）把程序的输入输出连到 IDE 不就行了？

答案是：大量命令行程序默认自己是跟"人"直接打交道的。它们会调用 isatty(fd) 检查 stdin/stdout 是否是 TTY 设备：

场景用 Pipe用 PTY
ls | grep foo✅ 够用✅ 也可以
跑 vim❌ vim 拒绝启动（"Output is not a terminal"）✅ vim 正常启动
跑 ssh❌ ssh 无法处理密码输入✅ 正常交互
Shell 提示符着色❌ ls 不输出彩色✅ 完整彩色输出
调整窗口大小❌ 程序不知道窗口大小✅ SIGWINCH 自动通知
Ctrl+C 中断❌ 需要自行处理✅ 内核自动发 SIGINT
⚠️ 不用 PTY 的后果
你的 IDE 终端里跑不了 vim、htop、ssh、top、less 等任何交互式程序。Shell 的提示符也不会有颜色。这就是为什么终端模拟器（iTerm2、Windows Terminal、VS Code 终端）底层都必须用 PTY。

四、Master-Slave 工作原理

4.1 完整架构图

┌──────────────────────────────────────────────────────────────────────┐ │ 你的程序 (IDE / 终端模拟器) │ │ │ │ ┌─────────────┐ 读写 ┌──────────────────────────────────────┐ │ │ │ 应用逻辑 │◄─────►│ Master 端 (/dev/ptmx 或 ConPTY) │ │ │ │ - 渲染屏幕 │ │ - 发送键盘输入 │ │ │ │ - 捕获输出 │ │ - 接收程序输出 │ │ │ │ - 调整大小 │ │ - 发送窗口大小变化 (SIGWINCH) │ │ │ └─────────────┘ └───────────────┬──────────────────────┘ │ │ │ │ │ ┌────────────────────┼────────────────────┐ │ │ │ 内核 (Line Discipline + PTY 驱动) │ │ │ │ - 处理回显、行编辑、Ctrl+C │ │ │ │ - 转换 \n ↔ \r\n │ │ │ └────────────────────┼────────────────────┘ │ │ │ │ │ ┌─────────────┐ 读写 ┌───────────────┴──────────────────────┐ │ │ │ Shell/程序 │◄─────►│ Slave 端 (/dev/pts/N 或 ConPTY) │ │ │ │ (bash/zsh) │ │ - 程序的 stdin/stdout/stderr │ │ │ │ 以为这是 │ │ - 程序 isatty() → true │ │ │ │ 真终端！ │ │ - 可以跑 vim、htop、ssh 等 │ │ │ └─────────────┘ └──────────────────────────────────────┘ │ └──────────────────────────────────────────────────────────────────────┘

4.2 数据流向

方向数据路径
键盘 → Shell按键字节IDE 写入 Master → 内核 Line Discipline → Slave → Shell stdin
Shell → 屏幕输出字节（含 ANSI 转义序列）Shell stdout → Slave → 内核 Line Discipline → Master → IDE 读取
窗口大小变化SIGWINCH 信号IDE 调用 resize() → 内核更新 winsize → 发 SIGWINCH 给 Shell
Ctrl+CSIGINT 信号IDE 写入 0x03 字节 → 内核 Line Discipline 拦截 → 发 SIGINT 给 Shell

4.3 Line Discipline —— PTY 的灵魂

Master 和 Slave 之间不是直连的，中间有一个 Line Discipline（线路规程）——内核里的一个"中间人"，负责：

功能说明类比
回显（Echo）你按的字符是否显示在屏幕上（密码输入时要关掉）打电话时听到自己的声音
行编辑（Line Editing）Backspace 删除、Ctrl+U 清空行打字机上的退格键
字符转换输出时 \n → \r\n；输入时 \r → \n翻译官
信号生成收到 Ctrl+C → 转换为 SIGINT 发给子进程秘书听到"挂断"就挂电话
EOF收到 Ctrl+D → 子进程读到 EOF对方说"再见"
💡 小贴士
没有 Line Discipline，Master 和 Slave 之间就是原始的字节流。Line Discipline 的存在，使得 Slave 端连上的程序"以为"自己连了真正的终端。

4.4 窗口大小（Winsize）与 SIGWINCH

// 告诉内核：终端窗口大小变了
ioctl(master_fd, TIOCSWINSZ, &winsize);
// 内核随即向子进程发送 SIGWINCH 信号
// Shell 收到后调用 ioctl(TIOCGWINSZ) 读取新尺寸，更新 $LINES/$COLUMNS

这就是为什么你拖拽终端窗口大小时，vim、htop 能立刻知道新尺寸——PTY 机制自动完成了这一切。

五、R-Code 的终端系统架构

5.1 整体架构

┌─────────────────────────────────────────────────────────────┐ │ R-Code IDE (WebView / Renderer) │ │ - xterm.js 渲染终端界面 │ │ - 用户键盘输入 → 发送给 Main │ └────────────────────────┬────────────────────────────────────┘ │ IPC (Unix Socket / Named Pipe) ┌────────────────────────┴────────────────────────────────────┐ │ Main 进程 (Tauri Rust) │ │ ┌──────────────────────────────────────────────────────┐ │ │ │ TerminalManager │ │ │ │ - 管理多个 PTY 实例 │ │ │ │ - 每个终端 = 一个 PTY + 一个 Shell 子进程 │ │ │ │ - 捕获输出 → 通过 IPC → Renderer 显示 │ │ │ │ - 接收输入 ← 通过 IPC ← Renderer 转发 │ │ │ └──────────────────────────────────────────────────────┘ │ └─────────────────────────────────────────────────────────────┘

5.2 portable-pty crate

R-Code 使用 portable-pty 这个 Rust crate 来跨平台管理 PTY。它的核心 API：

use portable_pty::{
    native_pty_system, Child, CommandBuilder, MasterPty, PtyPair, PtySize, PtySystem,
};

// 1. 获取当前系统的 PTY 实现
let pty_system = native_pty_system();

// 2. 打开一对 PTY（返回 Master + Slave）
let pair = pty_system.openpty(PtySize {
    rows: 24, cols: 80, pixel_width: 0, pixel_height: 0,
})?;

// 3. 用 Slave 端启动 Shell 子进程
let cmd = CommandBuilder::new("/bin/zsh");
let child = pair.slave.spawn_command(cmd)?;

5.3 TerminalManager 与 TerminalHandle

组件职责类比
TerminalManager管理所有 PTY 实例，创建/销毁/查找总机管理员
TerminalHandle单个终端的完整状态（PTY + Shell + 缓冲）一个分机
portable-pty跨平台 PTY 抽象层电话交换机

六、ConPTY vs Unix PTY —— 平台差异

维度Unix PTY (macOS/Linux)ConPTY (Windows)
Master 设备/dev/ptmx（open 后自动分配一对）ConPTY API（Windows 10 1809+）
Slave 设备/dev/pts/N（动态分配）伪句柄（由 ConPTY 管理）
创建方式open("/dev/ptmx") + grantpt() + unlockpt()CreatePseudoConsole()
调整大小ioctl(TIOCSWINSZ)ResizePseudoConsole()
历史自 1980 年代 Unix 就有Windows 10 1809（2018）才引入
💡 为什么 Windows 的 PTY 这么晚才出现？
Windows 之前有自己的"控制台"（Console）系统，跟 Unix PTY 完全不同。ConPTY 是微软为了让 Windows Terminal、VS Code 等现代终端模拟器能正常工作而推出的。在此之前，Windows 上的终端模拟器（比如 Git Bash 的 mintty）只能用 hack 方式实现。

七、OSC 133 Shell Integration —— 让 IDE 知道命令边界

终端输出是一大片连续的字符流。IDE 怎么知道"哪段是命令、哪段是输出、命令什么时候结束"？答案就是 OSC 133。

7.1 什么是 OSC 133？

OSC 133 是一组特殊的 ANSI 转义序列，由 Shell 在特定时刻注入到输出流中，用来标记命令的边界：

┌──────────────────────────────────────────────────────────────────────┐ │ 终端输出流（带 OSC 133 标记） │ │ │ │ [OSC 133 A] ← "命令开始" │ │ ┌──────────────────────────────────────┐ │ │ │ $ npm install ← 命令本身 │ │ │ │ added 42 packages ← 命令输出 │ │ │ │ ... │ │ │ └──────────────────────────────────────┘ │ │ [OSC 133 B] ← "命令结束（带退出码）" │ │ │ │ [OSC 133 A] ← "下一条命令开始" │ │ ┌──────────────────────────────────────┐ │ │ │ $ git status ← 命令本身 │ │ │ │ On branch main ← 命令输出 │ │ │ └──────────────────────────────────────┘ │ │ [OSC 133 B] ← "命令结束" │ └──────────────────────────────────────────────────────────────────────┘

7.2 各 Shell 的注入方式

Shell注入方式配置位置
zshprecmd / preexec 钩子.zshrc
bashPROMPT_COMMAND + DEBUG trap.bashrc
fishfish_prompt / fish_preexec 事件config.fish
PowerShellprompt 函数 + Set-PSReadLineOption$PROFILE
⚠️ 常见坑
如果用户的 Shell 没有配置 OSC 133 注入，IDE 就无法识别命令边界。R-Code 会在创建终端时自动注入配置，但如果用户覆盖了 Shell 配置文件，可能会丢失这些设置。

八、Block 解析器 —— 从字符流到结构化数据

有了 OSC 133 标记后，R-Code 的 Block 解析器就能把连续的字符流切分成一个个结构化块：

8.1 两种 Block 类型

类型含义内容
Command Block一条完整的命令命令本身 + 输出 + 退出码
Turn BlockAgent 的一次交互Agent 输入 + Agent 输出

8.2 状态机

┌──────────────────────────────────────────────────────────────────────┐ │ Block 解析器状态机 │ │ │ │ ┌──────┐ 收到命令开始 ┌──────┐ 收到命令结束 ┌──────┐ │ │ │ IDLE │ ─────────────────► │ BUSY │ ─────────────────► │EXITED│ │ │ └──────┘ └──────┘ └──────┘ │ │ ▲ │ │ │ │ │ │ 收到 Agent 开始 │ │ │ │ ▼ │ │ │ │ ┌──────┐ │ │ │ │ │AGENT │ ──────────────────────┘ │ │ │ └──────┘ 收到 Agent 结束 │ │ │ │ │ └────────────────────────────────────────────────────────────│ │ 回到 IDLE │ └──────────────────────────────────────────────────────────────────────┘
状态含义触发转换的事件
IDLE等待新命令收到 OSC 133 A → 进入 BUSY
BUSY命令执行中收到 OSC 133 B → 进入 EXITED
AGENTAgent 交互中收到 Agent 结束标记 → 进入 EXITED
EXITED命令已完成自动归档 → 回到 IDLE

九、滚动缓冲与前台进程跟踪

9.1 滚动缓冲（Scrollback）

终端输出会不断累积。R-Code 维护一个 200KB 上限 的滚动缓冲区，用户可以回看历史输出：

┌──────────────────────────────────────────────────────────────────────┐ │ 终端滚动缓冲区（200KB 上限） │ │ │ │ ┌──────────────────────────────────────────────────────────────┐ │ │ │ $ npm install │ │ │ │ added 42 packages in 3s │ │ │ │ $ git status │ │ │ │ On branch main │ │ │ │ Your branch is up to date with 'origin/main'. │ │ │ │ ... │ │ │ │ （最旧的内容被截掉） ← 200KB → │ │ │ └──────────────────────────────────────────────────────────────┘ │ │ ▲ │ │ │ 新内容追加到底部，超出 200KB 时从顶部截断 │ └──────────────────────────────────────────────────────────────────────┘
💡 为什么是 200KB？
200KB 大约能存 1-2 万行终端输出，足够覆盖大多数开发场景。再大的缓冲区会消耗过多内存，而且用户很少需要回看那么远的历史。

9.2 前台进程跟踪

R-Code 需要知道终端里当前在跑什么进程（用于显示状态、发送信号等）。它通过进程树来跟踪：

// 进程树示例
zsh (PID 1000)           ← Shell 进程
  └─ npm install (PID 1001) ← 前台子进程
      └─ node (PID 1002)    ← npm 启动的 node 进程

当用户按下 Ctrl+C 时，R-Code 需要把 SIGINT 发送给前台进程（PID 1001），而不是 Shell 本身。

十、终端编排原语 —— IDE 如何"指挥"终端

R-Code 的 Agent 需要能自动操作终端（比如运行命令、读取输出）。为此定义了六个终端编排原语：

原语作用类比
terminal.send发送按键到终端帮用户按键盘
terminal.write写入字符串到终端帮用户打字
terminal.command执行一条完整命令（写入 + 回车）帮用户输入命令并回车
terminal.list列出所有终端查看所有分机
terminal.create创建新终端新开一个分机
terminal.kill终止终端挂断分机

背压与流控制

当终端输出速度很快时（比如 npm install 打印大量日志），如果 IDE 来不及处理，数据就会堆积。R-Code 通过背压（Backpressure）机制控制流速：

┌──────────────┐ 快速产出 ┌──────────────┐ 慢速消费 ┌──────────────┐ │ Shell │ ──────────────► │ 缓冲区 │ ──────────────► │ IDE 渲染 │ │ (每秒 1MB) │ │ (有上限) │ │ (每秒 100KB) │ └──────────────┘ └──────────────┘ └──────────────┘ │ │ 缓冲区满时 ▼ 暂停读取 Master （背压传导到 Shell）

十一、常见问题排查

11.1 终端没有输出

⚠️ 排查清单
  • 检查 PTY 是否成功创建：查看 Main 日志是否有 pty open 相关错误
  • 检查 Shell 是否启动成功：Shell 路径是否正确（/bin/zsh、/bin/bash）
  • 检查 IPC 连接是否正常：Master 读取的数据是否能通过 IPC 传到 Renderer

11.2 中文显示乱码

通常是编码问题。R-Code 终端默认使用 UTF-8。如果 Shell 的 LANG 环境变量设置不正确，可能导致乱码：

// 检查编码设置
echo $LANG
// 应该输出类似 en_US.UTF-8 或 zh_CN.UTF-8

11.3 窗口大小不同步

如果调整终端面板大小后，vim、htop 没有更新尺寸，可能是 resize 事件没有正确传递：

// 手动检查窗口大小
echo $LINES $COLUMNS
// 应该反映当前终端的实际尺寸

11.4 外部 CLI Agent 检测

R-Code 需要检测终端里是否在运行外部 CLI Agent（比如 claude、codex）。它通过扫描进程树来实现：

// 检测逻辑（伪代码）
fn detect_external_agent(process_tree: &ProcessTree) -> Option<AgentType> {
    for proc in process_tree.foreground() {
        match proc.name() {
            "claude" => return Some(AgentType::Claude),
            "codex" => return Some(AgentType::Codex),
            _ => {}
        }
    }
    None
}

✅ 关键要点
  • PTY 是内核提供的"假终端"，让程序以为自己在跟真人交互
  • Master 端由 IDE 持有，Slave 端由 Shell 持有
  • Line Discipline 处理回显、行编辑、字符转换、信号生成
  • OSC 133 让 IDE 能识别命令边界
  • Block 解析器把字符流切分成结构化块（Command Block / Turn Block）
  • PTY 和 IPC 是不同层面的机制：PTY 控制 Shell，IPC 连接进程
