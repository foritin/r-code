第 7 章：安全模型

R-Code 执行 AI 提出的真实操作（读文件、改文件、跑命令），因此必须有坚固的安全边界。这一章深入解析它的多层防御体系。

7.1 为什么桌面 IDE 需要安全边界

传统 IDE（如 VS Code）主要是你告诉它做什么：你按保存、你点运行。但 R-Code 不一样 —— 它是 AI Agent 提出操作，系统代为执行。这意味着：

  • Agent 可能提出读取敏感文件（.env、~/.ssh/id_rsa）
  • Agent 可能提出执行危险命令（rm -rf /、sudo）
  • Agent 可能被恶意仓库的 .github/copilot-instructions.md 提示注入
  • Agent 可能在未经你同意的情况下修改代码

R-Code 的安全模型就是在这四个场景下保护你的系统和数据。

7.3 PathGuard 路径守卫

PathGuard（位于 r-code-core/src/security.rs）是文件操作的第一道关卡。它确保所有文件访问都被限制在 工作区根目录 之内。

核心原理

用户/Agent 请求路径 → PathGuard::resolve() → canonicalize (解析符号链接+..) → starts_with(root)? → 允许 / 拒绝 PathEscape

Fail-Closed 原则

🚫 关键不变量
PathGuard 遵循 fail-closed 原则：任何无法确证 containment 的路径一律返回 ProductError::PathEscape。这包括：权限不足、IO 错误、路径不存在但祖先逃逸。宁可错杀，不可放过。

TOCTOU 防护

TOCTOU（Time-of-Check to Time-of-Use）是一种竞态条件攻击。PathGuard 的防护策略是：在 canonicalize 之后重新校验 containment，从不信任输入路径的词法前缀。

符号链接解析

PathGuard::resolve 对已存在路径调用 canonicalize（自动解析全部符号链接与 ..），对不存在路径则找到最近的现存祖先再拼接尾段并校验。

// PathGuard 典型使用（每个文件工具内部）
let guard = PathGuard::new(workspace_root)?;
let safe_path = guard.resolve(&user_provided_path)?;
// safe_path 已确保在 workspace_root 内
std::fs::read_to_string(safe_path)?;

7.4 Permission Engine 风险分级

PermissionEngine（位于 r-code-gateway/src/permission.rs）是工具调用的第二道关卡。它对每个工具调用做风险分级和审批判断。

五级风险模型

级别名称行为典型工具
R0只读 / 无害自动允许list_files, search, git_status, TUI Agent 注入
R1低风险读自动允许read_file
R2命令执行查 standing rule；未命中则需用户审批terminal.send (裸 shell), write_file
R3高风险写查 standing rule；未命中则需用户审批（规则不持久化）delete_file, 大范围重构
R4危险（前置拒绝）直接拒绝sudo, git push, 破坏性命令, 读 secret

检查逻辑

PermissionEngine::check(task_id, tool_name, risk_level, target) │ ├─ R0/R1 ──→ Allowed（立即放行） │ ├─ R4 ────→ Denied("risk level R4: pre-rejected by policy") │ └─ R2/R3 ──→ 查 standing rule │ ├─ AllowAlways / Allow ──→ Allowed │ ├─ Deny ──────────────→ Denied("denied by standing rule") │ └─ 无命中 ──→ 创建 PermissionRequest 存入 pending 队列 返回 NeedsApproval(request)

Standing Rules（长期规则）

用户可以在审批时勾选"始终允许此任务"，这会在 standing_rules HashMap 中创建一条规则。格式为 (task_id, tool_name, target?) → Decision。

⚠️ R3 规则不持久化
出于安全考虑，R3（高风险写）的 standing rule 不会被保存。每次遇到 R3 工具调用都需要用户重新审批。只有 R0/R1/R2 的规则可以持久化。

7.5 Command Classifier 动态风险分类

CommandClassifier（位于 r-code-gateway/src/classifier.rs）用于 terminal.send 这类动态工具 —— 当 Agent 往终端注入文本时，系统需要动态决定风险级别。

分类规则

场景基础风险说明
TUI/Agent 注入（is_tui_agent = true）R0目标前台是交互式 Agent（claude/codex），注入是内容输入
裸 shell 命令（is_tui_agent = false）R2目标是普通 shell，注入可能被当作命令执行
含控制字符（非 \n\r\t）封顶至 R2控制字符可能触发转义序列注入

最终风险 = max(base, control_char_risk)（两层封顶）。

// 动态分类示例
assert_eq!(classify_command("ls -la", false), RiskLevel::R2);  // 裸 shell → R2
assert_eq!(classify_command("hello", true), RiskLevel::R0);    // Agent 注入 → R0
assert_eq!(classify_command("hello\x03", true), RiskLevel::R2); // 控制字符 → R2

7.6 SecretStore 密钥存储

R-Code 需要安全地存储 Anthropic/OpenAI API Key。它使用两层保护：

第一层：系统密钥链
macOS Keychain / Windows Credential Manager / Linux Secret Service
第二层：Electron safeStorage
进程内加密，需要系统解锁状态才能解密
Renderer 端：脱敏展示
UI 只显示 "sk-...XXXX" 格式，不暴露完整 Key

keyring crate（Rust 端）和 safeStorage（Electron 端）分别负责不同场景：Rust 端用于 Worker 进程内部读取 API Key 调用 LLM；Electron 端用于 Host 进程管理凭据。

7.7 工具调用完整流程

一次完整的工具调用会经过以下步骤：

Agent 提出工具调用 → 1. Schema 校验 → 2. PathGuard 路径边界 → 3. Classifier 风险分级 → 4. PermissionEngine 权限检查 → 5a. Allowed → 执行 5b. NeedsApproval → 弹审批 5c. Denied → 返回错误 → 6. 记账（无论结果） 
// ToolGateway 内部流程（简化）
async fn execute_call(task_id, run_id, tool_name, input) {
    let tool = self.tools.get(tool_name)?;           // 1. 查工具
    let risk = tool.risk_level();                     // 2. 取风险等级
    let check = permission_engine.check(task_id, tool_name, risk, target).await; // 3. 权限检查
    let mut audit = ToolCall::new(...);               // 4. 创建审计记录
    match check {
        Allowed => {
            let result = tool.execute(input).await?;  // 5. 执行
            audit.ok();
            self.ledger.push(audit);                  // 6. 记账
            Ok(result)
        }
        NeedsApproval(req) => {
            audit.deny("needs approval");
            self.ledger.push(audit);
            Err(PermissionError)
        }
        Denied(reason) => {
            audit.deny(&reason);
            self.ledger.push(audit);
            Err(PermissionError)
        }
    }
}

7.8 R4 拒绝列表

以下操作被 R-Code Tool Gateway 无条件拒绝：

🚫 硬编码拒绝（R4）
  • sudo 提权
  • git push 推送到远程
  • 读取 API Key / 凭据文件
  • 大范围破坏性命令（rm -rf /, chmod 777, mkfs 等）
  • 修改系统级配置文件（/etc/, /usr/）
  • 安装全局包（npm install -g, pip install --system）
ℹ️ 重要区分
R-Code 的 Tool Gateway 只约束 R-Code 托管的工具调用。如果你在终端里手动运行外部 Claude Code 或 Codex，它们有自己的权限系统，R-Code 不会拦截。详见 外部 CLI 不受约束。

7.9 Renderer 沙箱

Renderer 运行 Web 代码，因此需要多层沙箱：

  • 无 Node 集成：nodeIntegration: false
  • Context Isolation：渲染代码与 preload 桥隔离在独立上下文
  • Sandboxing：sandbox: true（启用 Chromium 沙箱）
  • CSP：Content Security Policy 限制可加载资源
  • iframe 沙箱：预览帧仅接受本地开发服务器
  • 导航限制：Renderer 无法自由跳转到外部网站
  • Window-open 限制：不允许随意打开新窗口

7.10 审计账本

ToolGateway 维护一个 审计账本（ledger: Arc<RwLock<Vec<ToolCall>>>）。所有工具调用（含被拒绝和待审批）都被记录。

每条审计记录包含：

  • id：UUID v4
  • run_id：所属 Agent Run
  • task_id：所属任务
  • tool_name：工具名称
  • input_json：调用参数
  • output_json：执行结果（被拒绝时可能为空）
  • risk_level：风险等级
  • status：running / ok / error / denied
  • caller：调用者身份
  • started_at / ended_at：时间戳

审计账本可通过 ToolGateway::ledger() 查询，用于合规审查、安全事件回溯。

7.11 外部 CLI 不受约束

⚠️ 关键安全边界
R-Code 的终端系统可以管理外部 CLI Agent（如 Claude Code、Codex），但 R-Code 的 Tool Gateway 不约束这些外部 CLI 的行为。它们有自己独立的权限系统。R-Code 仅提供 PTY 通道和 OSC 133 状态观察，不拦截其内部操作。

7.12 本章总结

✅ 安全模型核心要点
  • PathGuard：fail-closed + canonicalize + TOCTOU 防护，确保文件访问不越界
  • PermissionEngine：R0/R1 自动放行，R2/R3 查规则或需审批，R4 前置拒绝
  • CommandClassifier：动态风险分类（TUI Agent→R0, 裸 shell→R2, 控制字符→R2 封顶）
  • SecretStore：系统密钥链 + safeStorage + Renderer 脱敏
  • 审计账本：所有调用（含拒绝）入账
  • Renderer 沙箱：无 Node 集成、context isolation、CSP
  • 外部 CLI：不受 R-Code Tool Gateway 约束
