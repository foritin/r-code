第 10 章：CI 流水线

R-Code 的 CI 流水线由 GitHub Actions 驱动，包含 6 个并行 Job，覆盖格式化、静态分析、测试、安全审计、依赖检查和子模块校验。

10.1 GitHub Actions 工作流总览

CI 配置文件位于 .github/workflows/ci.yml，包含 6 个并行 Job：

#Job 名称Runner检查内容耗时
1fmtubuntu-latest代码格式是否符合 rustfmt 规范~30s
2clippyubuntu-latest静态分析警告（-W errors）~3min
3testmacos + windows全功能测试矩阵~5min
4auditubuntu-latest已知安全漏洞扫描~2min
5denyubuntu-latest依赖许可证/来源检查~2min
6submodule-pinubuntu-latestagent-core 子模块 commit 锁定~10s
类比：工厂质检流水线

把 CI 想象成工厂的质检线：fmt 检查"外观"（格式），clippy 检查"结构"（代码质量），test 检查"功能"（是否正常工作），audit 检查"安全"（有没有漏洞），deny 检查"合规"（依赖是否合规），submodule-pin 检查"零件版本"（依赖锁定）。

10.2 触发条件

name: CI

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main, develop]

CI 在以下情况自动触发：

  • 直接 push 到 main 或 develop 分支
  • 针对 main 或 develop 分支发起 Pull Request

10.3 Job 1: fmt 格式化检查

确保所有 Rust 代码符合统一的格式规范。

fmt:
  name: Format Check
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
      with:
        submodules: recursive
    - uses: dtolnay/rust-toolchain@stable
      with:
        components: rustfmt
    - name: cargo fmt --check
      run: cargo fmt --all -- --check
失败时怎么办

如果 fmt 失败，本地运行 cargo fmt --all 即可自动修复格式问题，然后重新提交。

10.4 Job 2: clippy 静态分析

Clippy 的 Rust 代码 linter，检查常见错误和低效模式。R-Code 将 clippy 警告视为错误（-D warnings）。

clippy:
  name: Clippy
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
      with:
        submodules: recursive
    - uses: dtolnay/rust-toolchain@stable
      with:
        components: clippy
    - uses: Swatinem/rust-cache@v2
    - name: cargo clippy
      run: cargo clippy --workspace --all-targets -- -D warnings
--all-targets 的含义

--all-targets 表示检查所有 target（lib、bin、test、example、bench），确保测试代码也符合规范。

10.5 Job 3: test 测试矩阵

在多个操作系统上运行全量测试，使用矩阵策略：

test:
  name: Test
  runs-on: ${ matrix.os }
  strategy:
    matrix:
      os: [macos-latest, windows-latest]
  steps:
    - uses: actions/checkout@v4
      with:
        submodules: recursive
    - uses: dtolnay/rust-toolchain@stable
    - uses: Swatinem/rust-cache@v2
    - name: cargo test
      run: cargo test --workspace --all-features
平台说明
macos-latest验证 Apple Silicon / Intel Mac 兼容性
windows-latest验证 Windows x64 兼容性

10.6 Job 4: audit 安全审计

使用 cargo audit 检查依赖中是否存在已知安全漏洞：

audit:
  name: Security Audit
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
      with:
        submodules: recursive
    - uses: dtolnay/rust-toolchain@stable
    - uses: Swatinem/rust-cache@v2
    - name: Install cargo-audit
      run: cargo install cargo-audit
    - name: cargo audit
      run: cargo audit
安全审计失败

如果 audit 报告了 High/Critical 级别的漏洞，必须立即修复。修复方式通常是升级受影响的依赖版本。

10.7 Job 5: deny 依赖检查

cargo deny 检查依赖的合规性，配置在 deny.toml：

deny:
  name: Dependency Deny
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
      with:
        submodules: recursive
    - uses: dtolnay/rust-toolchain@stable
    - uses: Swatinem/rust-cache@v2
    - name: Install cargo-deny
      run: cargo install cargo-deny
    - name: cargo deny check
      run: cargo deny check

deny.toml 配置详解

[advisories]
version = 2
yanked = "deny"           # 禁止 yanked 版本的依赖

[licenses]
version = 2
allow = [
    "MIT", "Apache-2.0", "Apache-2.0 WITH LLVM-exception",
    "BSD-2-Clause", "BSD-3-Clause", "ISC", "Unicode-DFS-2016",
    "Unicode-3.0", "Zlib", "CC0-1.0", "MPL-2.0",
]

[bans]
deny = [
    { name = "pi-sdk" },      # 禁止 Pi SDK 依赖（路径 B 决策）
    { name = "pi-sdk-core" },
    { name = "pi-sdk-agent" },
    { name = "pi-agent" },
]

[sources]
unknown-registry = "deny"   # 禁止未知 registry
allow-registry = ["https://github.com/rust-lang/crates.io-index"]

10.8 Job 6: submodule-pin 子模块校验

验证 agent-core 子模块的 commit 是否与 contract-lock.json 中锁定的一致：

submodule-pin:
  name: Submodule Pin Check
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
      with:
        submodules: recursive
    - name: Verify agent-core submodule pin
      run: |
        EXPECTED=$(grep -oP '"commit":\s*"([a-f0-9]+)"' \
          vendor/agent-core/contract-lock.json | grep -oP '[a-f0-9]{40}')
        ACTUAL=$(cd vendor/agent-core && git rev-parse HEAD)
        if [ -n "$EXPECTED" ] && [ "$EXPECTED" != "$ACTUAL" ]; then
          echo "ERROR: agent-core submodule commit mismatch!"
          exit 1
        fi
        echo "✅ Submodule pin verified"
为什么需要子模块 pin

子模块 pin 确保所有开发者和 CI 使用完全相同版本的 agent-core 代码，避免"我这里能跑"的问题。

10.9 缓存策略

R-Code 使用 Swatinem/rust-cache@v2 缓存 Rust 编译产物：

- uses: Swatinem/rust-cache@v2

缓存策略：

  • 基于 Cargo.lock 的哈希作为缓存 key
  • 缓存 target/ 目录下的编译产物
  • 不同 Job 共享同一份缓存（节省 ~60% CI 时间）
  • 缓存有效期 7 天，过期自动重建

10.10 本地模拟 CI

在提交前，可以在本地运行 CI 中的检查，避免反复触发 CI：

# 1. 格式化检查
cargo fmt --all -- --check

# 2. clippy 检查
cargo clippy --workspace --all-targets -- -D warnings

# 3. 全量测试
cargo test --workspace --all-features

# 4. 安全审计
cargo audit

# 5. 依赖检查
cargo deny check

10.11 故障排查

Job 失败常见原因修复方法
fmt代码格式不标准运行 cargo fmt --all
clippy新增代码有警告按提示修复，或 #[allow(...)] 并说明原因
test测试用例失败本地复现：cargo test <具体测试名>
audit依赖有已知漏洞cargo update -p <包名> 升级
deny引入未授权许可证的依赖更换依赖或申请许可证白名单
submodule-pin子模块未更新锁定更新 contract-lock.json 或回滚子模块
