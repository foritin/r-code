第 3 章：IPC 进程间通信

R-Code 由多个进程组成，它们之间如何"对话"？这一章我们拆解 IPC（Inter-Process Communication，进程间通信）的完整机制——从"为什么要通信"到"一条消息怎么从发出到收到"。

一、什么是 IPC？—— 办公室之间的电话

想象一家公司有三个员工在不同办公室工作：

前台小姐姐
Renderer · UI
↔
管家
Main · Rust 后端
↔
打工人
Worker · AI Agent

每个员工在各自的办公室（进程）里工作，各有各的职责。但公司要运转，他们必须互相打电话、发邮件。IPC 就是这些"电话线"和"邮件系统"。

💡 核心概念
进程（Process）是运行中的程序实例，拥有独立的内存空间。一个进程不能直接读写另一个进程的内存——就像你不能跑到别人办公室直接翻人家抽屉。必须通过"电话"（IPC）来沟通。

现实中的类比

现实场景IPC 对应
两个人在同一个房间说话共享内存（直接读写同一块数据）
两个人在不同城市打电话Socket（网络或本地 socket）
一个人给另一个人寄信管道（Pipe）/ 消息队列
公司里发邮件（写明收件人 + 附件）JSON-RPC over IPC（R-Code 的方案）

R-Code 选的是「寄邮件」的方式：进程之间用结构化的消息互相调用。每一封"邮件"都有明确的收件人（method）、内容（params）、编号（id），对方收到后回一封"回信"（response）。

二、为什么 R-Code 需要 IPC？

2.1 三进程架构

R-Code 有三个进程，各司其职：

┌─────────────────────────────────────────────────────────────┐ │ Main 进程 (Tauri Rust 后端) │ │ ┌──────────────────────────────────────────────────────┐ │ │ │ 宿主服务层（管家） │ │ │ │ - Secret Store - Task Engine │ │ │ │ - Tool Gateway - Permission Engine │ │ │ │ - Change Service - Workspace Service │ │ │ │ - Document Service - Git Service │ │ │ │ - Search Service - Terminal Service │ │ │ │ - Verification Service │ │ │ └──────────────────────────────────────────────────────┘ │ │ ▲ │ │ IPC (Unix Socket / Named Pipe) │ │ ▼ │ │ ┌──────────────────────────────────────────────────────┐ │ │ │ Agent Worker 进程（独立进程 · 打工人） │ │ │ │ - Agent Runtime (Pi Adapter / Mock) │ │ │ │ - 无文件/命令执行器 │ │ │ │ - 无密钥存储 │ │ │ └──────────────────────────────────────────────────────┘ │ │ │ │ ┌──────────────────────────────────────────────────────┐ │ │ │ Renderer 进程（WebView · 前台小姐姐） │ │ │ │ - React + TypeScript UI │ │ │ │ - Monaco Editor │ │ │ │ - xterm.js 终端 │ │ │ └──────────────────────────────────────────────────────┘ │ └─────────────────────────────────────────────────────────────┘

2.2 为什么拆开三个进程？

设计目标解释
安全Agent Worker 直接面对 AI 模型（不可信输入），让它越权访问文件系统就炸了。单独一个进程，手里没有文件和命令执行器，只能「发消息请求 Main 帮忙执行」
隔离Renderer（WebView）崩了不能把整个 IDE 拖死
独立生命周期Worker 可以崩溃重启，不影响 UI 响应
⚠️ 关键洞察
拆开了之后，它们之间怎么对话？答案就是 IPC。没有 IPC，三进程就是三个孤岛，无法协作。IPC 是 R-Code 的神经系统。

三、R-Code 的三种 IPC 通道

R-Code 内部有三条"电话线"，每条连接不同的进程对：

┌──────────────────────────────────────────────────────────────────┐ │ │ │ Renderer ──────── Tauri 命令/事件 ──────── Main │ │ (WebView) (JS ↔ Rust 桥接) (Rust 后端) │ │ │ │ Main ──────── hermes-ipc ──────── Agent Worker │ │ (Rust) (JSON-RPC over (独立进程) │ │ Unix Socket / Named Pipe) │ │ │ │ Worker ──── 进程内调用 ──── Agent-core │ │ (同一进程，直接函数调用，无需序列化) │ │ │ └──────────────────────────────────────────────────────────────────┘
通道连接协议方向
Tauri 桥接Main ↔ Renderer自定义命令 + 事件双向
hermes-ipcMain ↔ WorkerJSON-RPC 2.0双向
进程内调用Worker ↔ Agent-core直接函数调用单向（Worker 调 Agent-core）

3.1 Main ↔ Renderer：Tauri 桥接

这是 Tauri 框架自带的能力。前端（TypeScript）通过 invoke() 调用 Rust 函数，Rust 通过 emit() 向前端推送事件。

// 前端调用 Rust（TypeScript）
const result = await invoke('create_task', {
  title: '修复登录 Bug',
  repo: 'my-project'
});

// Rust 向前端推送事件
app.emit('task:created', &task)?;
💡 小贴士
Tauri 桥接不需要你关心底层传输细节——框架已经帮你处理好了。你可以把它当作"前端直接调 Rust 函数"。

3.2 Main ↔ Worker：hermes-ipc

这是 R-Code 中最重要的 IPC 通道。Main 和 Worker 是两个独立进程，通过 Unix Socket（macOS/Linux）或 Named Pipe（Windows）传输 JSON-RPC 2.0 消息。

// Worker 发送请求到 Main
{
  "jsonrpc": "2.0",
  "id": "req-42",
  "method": "task.create",
  "params": { "title": "修复登录 Bug" }
}

// Main 返回响应给 Worker
{
  "jsonrpc": "2.0",
  "id": "req-42",
  "result": { "taskId": "task-123" }
}

3.3 Worker ↔ Agent-core：进程内调用

Worker 和 Agent-core 在同一个进程里，不需要走网络/socket，直接函数调用即可。这是最快的方式，但仅限于同一进程内部。

四、IPC 的"深度"—— 四层协议栈

R-Code 的 IPC 不是简单传字符串，而是严格的四层结构。每一层只关心自己的事，这就是分层设计的魅力：

第 4 层：应用语义 → task.create / tool.execute / agent.event
第 3 层：RPC 协议 → JSON-RPC 2.0（请求/响应/事件）
第 2 层：序列化帧 → [4 字节长度][JSON 载荷]
第 1 层：传输层 → Unix Socket / Named Pipe

第 1 层：传输层 —— 数据怎么流动？

macOS 方案：Unix Socket

// Main 进程：在 /tmp/charter.sock 这个路径上"挂牌营业"
let listener = UnixListener::bind("/tmp/charter.sock")?;
// Worker 进程：连上这个路径，Main 接受连接
let (stream, _addr) = listener.accept().await?;
💡 类比
你可以把 Unix Socket 想象成一个固定门牌号的信箱。Main 进程把信箱放在 /tmp/charter.sock，Worker 和 Renderer 都知道这个地址，往里塞信、取信。

Windows 方案：Named Pipe

// 名字是 \\.\pipe\charter，Windows 内核管理
let pipe = ServerOptions::new().create(r"\\.\pipe\charter")?;
✅ 关键洞察
传输层之上，协议层和应用层完全一致。业务代码不需要为两个平台各写一份——只有最底层的「连接建立」和「数据读写」需要条件编译。

启动时清理旧 socket

if socket_path.exists() {
    std::fs::remove_file(&socket_path)?;  // 上次崩溃留下的信箱得先拆掉
}

第 2 层：序列化帧 —— 怎么区分两条消息？

Socket 是字节流——水一样源源不断。你写了 3 个字节、再写 5 个字节，对面收到的是一摊 8 个字节的混合物。怎么知道"第一条消息在哪里结束"？

R-Code 的方案叫 length-prefixed framing：

[4 字节长度，大端 u32][N 字节 JSON 载荷] 发送 "hello"： [0x00 0x00 0x00 0x05] [h e l l o] ← 4 字节表示长度是 5 → ← 5 字节数据 →

接收方先读 4 字节 → 知道长度是 5 → 再精确读 5 字节 → 拿到完整的 "hello"。完美解决"拆包"问题。

⚠️ 常见误区
有人会想用换行符 \n 来分隔消息——但 JSON 里可能包含换行符（比如代码片段），所以不可靠。length-prefixed 是工业标准做法（gRPC、WebSocket 帧都类似）。

第 3 层：RPC 协议 —— 怎么表达"调用方法"？

传输层只是把字节从 A 搬到 B。到了 B 之后，怎么知道"A 想让我做什么"？这就是 RPC（Remote Procedure Call，远程过程调用）协议的职责。

R-Code 采用 JSON-RPC 2.0——一个极其简单的协议，只有四种消息类型：

五、JSON-RPC 2.0 详解

5.1 四种消息类型

类型方向是否有 id用途
请求Client → Server✅ 有调用一个方法，等待结果
响应Server → Client✅ 有返回结果或错误
通知任意 → 任意❌ 无单向消息，不需要回复
错误Server → Client✅ 有方法执行失败

5.2 请求消息

{
  "jsonrpc": "2.0",     // 协议版本，固定 "2.0"
  "id": "req-42",          // 唯一标识，用于匹配请求和响应
  "method": "task.create", // 要调用的方法名
  "params": {              // 方法参数（可选）
    "title": "修复登录 Bug",
    "repo": "my-project"
  }
}

5.3 成功响应

{
  "jsonrpc": "2.0",
  "id": "req-42",          // 与请求的 id 一致
  "result": {             // 成功时返回 result
    "taskId": "task-123",
    "createdAt": "2026-07-25T10:30:00Z"
  }
}

5.4 错误响应

{
  "jsonrpc": "2.0",
  "id": "req-42",
  "error": {              // 失败时返回 error
    "code": -32602,
    "message": "Invalid params",
    "data": { "field": "title", "reason": "required" }
  }
}

5.5 通知（Notification）

通知是一种不需要回复的请求——没有 id 字段。适合"告诉对方一件事，但不需要结果"的场景：

{
  "jsonrpc": "2.0",
  "method": "agent.event",   // 没有 id！
  "params": { "type": "thinking", "text": "让我想想..." }
}
💡 小贴士
想象一下：请求 = 发微信问同事"帮我查一下数据"（等他回复）；通知 = 在群里发一句"我下班了"（不需要回复）。

5.6 错误码体系

R-Code 的 JSON-RPC 有两套错误码：

错误码含义何时出现
-32700Parse errorJSON 格式非法
-32600Invalid request不符合 JSON-RPC 2.0 规范
-32601Method not found调用的方法未注册
-32602Invalid params参数不符合 schema
-32603Internal error服务器内部错误
1001Task not found应用级错误：任务不存在

负数段（-32xxx）是 JSON-RPC 标准预留的协议错误；正数段（1xxx）是 R-Code 自己定义的应用错误。

六、IPC 消息流完整示例

假设用户在界面上点击"创建任务"，我们从用户点击开始，追踪这条消息直到 Worker 收到结果：

用户点击按钮 │ ▼ Renderer: invoke("create_task", { title: "修复登录 Bug" }) │ │ (Tauri 桥接) ▼ Main: TaskEngine.create_task(params) │ │ (通过 IPC 调用 Worker 确认 Agent 可用) ▼ Main → Worker: { id: "m-1", method: "agent.createTask", params: {...} } │ │ (hermes-ipc: JSON-RPC over Unix Socket / Named Pipe) ▼ Worker: Agent Runtime 处理 │ │ (同一进程内调用 Agent-core) ▼ Agent-core: 创建任务对象，分配 taskId │ │ (返回给 Worker) ▼ Worker → Main: { id: "m-1", result: { taskId: "task-123" } } │ │ (hermes-ipc 回程) ▼ Main: 持久化到 Secret Store，更新状态 │ │ (Tauri 事件) ▼ Renderer: emit("task:created", task) → UI 更新

关键步骤解读

步骤做什么走哪条通道
1用户点击按钮—
2Renderer 调用 MainTauri 桥接
3Main 验证权限，请求 Workerhermes-ipc（请求）
4Worker 处理 Agent 逻辑进程内调用
5Worker 返回结果给 Mainhermes-ipc（响应）
6Main 推送事件给 RendererTauri 事件

七、跨平台差异 —— macOS vs Windows

R-Code 支持 macOS 和 Windows 两个平台。IPC 的底层传输不同，但上层协议完全一致：

维度macOS / LinuxWindows
传输机制Unix SocketNamed Pipe
地址形式文件路径 /tmp/charter.sock管道名 \\.\pipe\charter
实现方式tokio::net::UnixListenertokio::net::windows::named_pipe
条件编译#[cfg(unix)]#[cfg(windows)]
协议层完全相同（JSON-RPC 2.0 + 序列化帧）
应用语义完全相同（task.create / tool.execute / agent.event）
✅ 设计智慧
通过分层设计，R-Code 让 95% 的代码是平台无关的。只有最底层的"建立连接"和"读写字节"需要条件编译。这就是为什么 R-Code 能同时支持 macOS 和 Windows，而不需要维护两套代码库。

八、安全边界 —— 不是谁都能发号施令

IPC 是 R-Code 的神经系统，但也是潜在的攻击面。如果 Worker（面对不可信 AI 输入）可以随意调用 Main 的任何方法，那就危险了。R-Code 通过三层防护确保安全：

8.1 请求校验

每个 IPC 请求到达 Main 后，会经过以下检查：

请求到达
→
JSON 解析
→
Schema 验证
→
权限检查
→
执行业务逻辑

8.2 Schema 验证

每个 method 都有严格的参数 schema。不符合 schema 的请求会被直接拒绝（返回 -32602 Invalid params）：

// task.create 的参数 schema
{
  "type": "object",
  "required": ["title"],
  "properties": {
    "title": { "type": "string", "minLength": 1 },
    "repo": { "type": "string" }
  }
}

8.3 固定 Channel 枚举

Worker 只能调用预先注册的方法。如果 Worker 尝试调用一个不存在的方法，Main 返回 -32601 Method not found。这防止了 AI 通过 prompt 注入随意调用任意方法。

8.4 幂等 Key 与乐观版本

网络可能不稳定，请求可能重复。R-Code 通过 幂等 key 确保同一个操作不会执行两次：

{
  "id": "req-42",           // 请求唯一标识
  "method": "task.create",
  "params": {
    "idempotencyKey": "abc123",  // 幂等 key
    "title": "修复登录 Bug"
  }
}
💡 类比
幂等 key 就像餐厅的"取餐号"。你点了一杯咖啡（请求），拿到取餐号 42。如果你不小心又点了一次（重复请求），服务员看到取餐号 42 已经做过了，就不会再做一杯。

九、大文件与流处理 —— 不只是小消息

IPC 不只能传小消息。R-Code 还需要处理大文件传输和实时流（比如终端输出）。这些场景有特殊处理：

9.1 MessagePort（大文件传输）

当需要传输大文件（比如代码仓库的 diff）时，JSON-RPC 的 JSON 序列化会成为瓶颈。R-Code 使用 MessagePort 建立高速通道：

┌──────────────┐ ┌──────────────┐ │ Worker │ │ Main │ │ │ 1. 建立 MessagePort │ │ │ │ ◄──────────────────► │ │ │ │ │ │ │ │ 2. 通过高速通道传输 │ │ │ 大文件 ──────► 原始字节流 ──────► 接收并处理 │ │ │ │ │ └──────────────┘ └──────────────┘

9.2 分块流（Chunked Stream）

对于实时流（比如 Agent 的思考过程），R-Code 使用分块传输：

// 流式响应示例：Agent 边思考边输出
{ "id": "s-1", "event": "agent.thinking", "chunk": "让我分析" }
{ "id": "s-1", "event": "agent.thinking", "chunk": "这个问题" }
{ "id": "s-1", "event": "agent.thinking", "chunk": "的根因..." }
{ "id": "s-1", "event": "agent.done", "result": { ... } }

十、常见调试方法

IPC 出问题时，怎么排查？以下是几个实用技巧：

10.1 查看 Socket 是否存在

# macOS/Linux
ls -la /tmp/charter.sock

# Windows（PowerShell）
Get-ChildItem \\.\pipe\ | Where-Object { $_.Name -like "*charter*" }

10.2 抓包分析

# macOS：用 socat 监听 Unix Socket
socat -d -d UNIX-LISTEN:/tmp/debug.sock,fork UNIX-CONNECT:/tmp/charter.sock

# 通用：用 Wireshark 抓 Named Pipe（Windows）

10.3 日志追踪

R-Code 的 IPC 层内置了详细的日志。开启 RUST_LOG=trace 可以看到每条消息的收发：

RUST_LOG=trace cargo run 2>&1 | grep 'ipc'
⚠️ 常见坑
  • Socket 残留：程序崩溃后 socket 文件可能残留，导致重启失败。启动时务必清理旧 socket。
  • 消息过大：单条消息超过 16MB 可能被截断。大文件走 MessagePort。
  • 连接断开：Worker 崩溃后 Main 会收到连接断开事件，需要优雅处理重连。
