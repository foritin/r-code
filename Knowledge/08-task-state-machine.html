第 8 章：任务状态机

R-Code 的核心是"任务"（Task）。本章带你深入理解 Task 的状态模型、合法转换规则、审查机制以及字节级回滚原理。

8.1 什么是 Task

在 R-Code 中，Task 代表用户给 Agent 的一个目标。你可以把它想象成一张"工单"：用户填写标题和目标描述，指定交互模式，Agent 领取工单后开始工作。

每个 Task 拥有唯一 ID、归属项目、完整的时间戳记录，以及当前所处状态。Task 是 R-Code 调度、审查、回滚的最小原子单元。

类比：工单系统

把 Task 想象成工单系统里的一张工单：创建时状态为"待处理"（Idle），开始处理后变为"处理中"（InProgress），完成后进入"待审查"（ReviewReady），审查通过后回到"已完成"（Idle）。

8.2 Task DTO 完整字段

Task DTO 定义在 crates/r-code-core/src/dto.rs，是冻结的产品数据结构。

pub struct Task {
    pub id: String,              // UUID v4
    pub project_id: String,      // 归属项目的 canonical path
    pub title: String,           // 用户可见标题
    pub goal: String,            // 目标描述（给 Agent 的指令）
    pub mode: TaskMode,          // 交互模式（ask / edit / auto）
    pub state: TaskState,        // 当前状态
    pub worktree_path: Option<String>, // Git worktree 路径
    pub created_at: DateTime<Utc>,
    pub updated_at: DateTime<Utc>,
}
字段类型说明
idStringUUID v4，全局唯一
project_idString项目路径（worktree 的 canonical 形式）
titleString用户填写的简短标题
goalString详细的目标描述，是 Agent 执行的核心指令
modeTaskMode决定 Agent 是否需要审批才能执行操作
stateTaskState当前所处生命周期状态
worktree_pathOption<String>Git worktree 路径，隔离工作区
created_atDateTime<Utc>创建时间，RFC 3339 格式存储
updated_atDateTime<Utc>最后更新时间

8.3 TaskMode 交互模式

TaskMode 决定 Agent 在执行工具调用时是否需要用户审批：

模式值行为
Ask"ask"只读问答模式，Agent 不会修改任何文件
Edit"edit"受控写入模式，高风险工具调用需要用户审批
Auto"auto"全自动模式，验证通过后自动接受
注意

TaskMode 在创建 Task 时指定，一般不建议运行时切换。因为模式变化会影响整个审查流程的语义。

8.4 TaskState 状态机详解

TaskState 是任务生命周期的核心。状态转换路径如下：

Idle ──► Exploring ──► InProgress ──► ReviewReady ──► Idle
  │           │              │                  │
  │           └──────────────┴──────────────────┘
  │           (取消 / 回退路径，回到 Idle)
  │
  └──► Archived (任意非终态都可以归档)
状态值含义
Idle"idle"空闲：未开始或已完成上一轮
Exploring"exploring"探索中：Agent 正在读取文件、理解上下文
InProgress"in_progress"进行中：Agent 正在执行工具调用
ReviewReady"review_ready"待审查：Agent 完成一轮，等待用户决定
Archived"archived"已归档：终态，不可再操作

合法转换 vs 非法转换

不是任意两个状态之间都可以跳转。R-Code 通过 validate_transition 函数严格控制。

转换合法性说明
Idle → Exploring✓ 合法开始探索
Exploring → InProgress✓ 合法开始执行
InProgress → ReviewReady✓ 合法完成一轮，等待审查
ReviewReady → Idle✓ 合法审查完成（接受/回滚）后回到空闲
Exploring → Idle✓ 合法取消探索
InProgress → Idle✓ 合法取消执行
任意非终态 → Archived✓ 合法归档
Idle → InProgress✗ 非法不能跳过 Exploring
ReviewReady → InProgress✗ 非法不能直接重新执行
Archived → 任意✗ 非法Archived 是终态，不可逆

8.5 validate_transition 函数逻辑

validate_transition 定义在 crates/r-code-core/src/state.rs，是整个状态机的守门人。

pub fn validate_transition(
    from: TaskState,
    to: TaskState
) -> Result<(), StateTransitionError> {
    // 1. Archived 是终态，直接拒绝
    if from == TaskState::Archived {
        return Err(StateTransitionError::Archived);
    }

    // 2. 模式匹配所有合法转换
    let valid = match (from, to) {
        (Idle, Idle)              => true,  // 同状态不算转换
        (Idle, Exploring)         => true,  // 正常流程
        (Exploring, InProgress)   => true,
        (InProgress, ReviewReady) => true,
        (ReviewReady, Idle)       => true,
        (Exploring, Idle)         => true,  // 取消
        (InProgress, Idle)        => true,  // 取消
        (_, Archived)             => true,  // 归档
        _ => false,  // 其他全部非法
    };

    if valid { Ok(()) }
    else { Err(StateTransitionError::IllegalTransition { from, to }) }
}
设计哲学

状态机采用"白名单"模式：只有明确列出的转换才合法，其余全部拒绝。这防止了因遗漏而意外开放危险路径。

错误类型

pub enum StateTransitionError {
    IllegalTransition { from: TaskState, to: TaskState },
    Archived,
    ActiveRunExists,
    PendingToolCalls,
}
错误触发条件
IllegalTransition尝试非法状态转换
ArchivedTask 已归档，任何操作都被拒绝
ActiveRunExists已存在活跃 Run，不能开始新的
PendingToolCalls存在未完成的高风险调用，不能进入 ReviewReady

8.6 ReviewState 审查状态

当 Task 进入 ReviewReady 后，用户需要做出决定。ReviewState 记录这个审查结果：

审查状态值含义终态
Pending"pending"等待用户决定否
Accepted"accepted"用户接受变更是
AutoAccepted"auto_accepted"验证通过，自动接受是
RolledBack"rolled_back"用户回滚变更是
Answered"answered"Ask 模式零变化自动结算是

    to: ReviewState

//   Pending → Accepted
//   Pending → AutoAccepted
//   Pending → RolledBack
//   Pending → Answered
// 终态不可转换
最佳实践

在 Edit 模式下，用户应逐文件审查 diff 后再接受。Auto 模式下系统会自动运行验证命令，通过则 AutoAccepted。

8.7 硬性不变量

R-Code 的状态机遵循三条硬性不变量（invariant），违反任何一条都会导致系统拒绝操作：

不变量 1：一个 Task 最多一个活跃 Run

同一时刻，一个 Task 只能有一个正在运行的 AgentRun。这是为了防止并发执行导致状态混乱。

不变量 2：未完成高风险调用不能进入审查

如果存在未完成（Running）的 R2/R3/R4 级别工具调用，Task 不能进入 ReviewReady 状态。

不变量 3：Archived 是终态

一旦 Task 被归档，任何状态转换都会被拒绝。这是为了防止误操作激活已废弃的任务。

8.8 AgentRun 生命周期

AgentRun 记录一次 Agent 执行的全过程。当 Task 从 Idle 开始执行时，系统创建一个 AgentRun：

pub struct AgentRun {
    pub id: String,                // UUID v4
    pub task_id: String,           // 所属 Task
    pub model: String,             // 使用的模型名称
    pub review_state: ReviewState, // 审查状态（默认 Pending）
    pub started_at: DateTime<Utc>,
    pub ended_at: Option<DateTime<Utc>>, // None = 仍在运行
    pub usage_json: Option<String>,       // Token 用量统计
}
创建 → Running → Pending 审查 → Accepted / AutoAccepted / RolledBack / Answered

8.9 文件基线与变更追踪

为了实现可靠的回滚，R-Code 在每次 Agent 执行前会捕获文件基线（File Baseline）：

文件基线（FileBaseline）
记录每个文件的 content_hash + blob_key
创建时机：Agent 开始修改文件之前
存储位置：SQLite file_baselines 表 + blob 文件

Agent 执行过程中，每次文件修改都会记录到 file_changes 表：

pub struct FileChange {
    pub id: String,
    pub task_id: String,
    pub tool_call_id: Option<String>,  // 哪个工具调用产生的
    pub path: String,                    // 文件路径
    pub change_type: String,             // modify / create / delete / rename
    pub before_hash: Option<String>,    // 变更前内容哈希
    pub after_hash: Option<String>,     // 变更后内容哈希
    pub old_path: Option<String>,       // 重命名时的旧路径
    pub created_at: DateTime<Utc>,
}

8.10 按轮回滚（byte-exact rollback）

R-Code 的回滚是字节级精确的：不是简单地在 Git 层面 revert，而是把每个文件恢复到基线时刻的原始内容。

类比：时间机器

想象你在修改一份重要文档前，先完整复制了一份（基线）。无论后来改了多少次，只要点击"回滚"，系统就用那份精确复制件覆盖回去——字节不差。

回滚流程：

  1. 用户点击"回滚"按钮
  2. 系统查询该 Run 关联的所有 FileBaseline 记录
  3. 从 blob 存储中读取原始文件内容
  4. 逐文件覆盖当前磁盘文件
  5. 更新 AgentRun.review_state = RolledBack
  6. Task 状态从 ReviewReady 回到 Idle
为什么用字节级回滚而非 Git revert

Agent 可能在 Git 工作区中产生了未 commit 的改动、临时文件、.gitignore 排除文件。Git revert 无法覆盖这些场景，但字节级回滚可以精确还原一切。

8.11 归档与恢复

归档（Archived）是 Task 的终态。归档后的 Task：

  • 不能再开始新的 AgentRun
  • 不能再进行任何状态转换
  • 仍然保留在数据库中，用于历史查询
  • 关联的 file_baselines、file_changes 等数据保留
注意：Archived 不可逆

目前 R-Code 不提供"反归档"操作。如果需要重新激活一个已归档的 Task，技术上需要手动操作数据库（将 state 从 archived 改回 idle）。

归档的常见场景：

  • 任务已完成且用户不再需要查看
  • 任务已废弃（用户改变了需求方向）
  • 清理工作区，保持活跃任务列表整洁
