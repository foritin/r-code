从空仓到可发布 Charter 的执行手册

1. 使用方式

本页把全站说明收束为可执行顺序。新团队只需取得三个同级目录：
agent-core/、r-code/、tiny-hermes/；重构 Charter 时前两个是必需输入，
第三个只在需要理解共享消费者时查阅。无需读取当前 Electron 源码或其它 Markdown。

每个阶段都遵循同一纪律：先合同 → 再最小实现 → 再故障测试 → 再 UI 投影 → 再发布证据。
不要以“功能演示成功”跳过数据、权限、恢复和验收。

2. 第 0 天：建立可复制的工程边界

  1. 新建 Rust workspace、UI workspace、CI 和独立用户数据测试目录。
  2. 把 agent-core 以固定 commit 放在 vendor/agent-core；阅读其 13、14、15 页。
  3. 创建 charter-core、charter-store、charter-gateway、charter-terminal、
    charter-agent-worker、charter-host 与 UI 包的空壳，不实现跨层快捷调用。
  4. 建立错误格式、结构化日志、feature flag、临时目录 fixture 和一键本地测试命令。
  5. 在第一行产品代码前冻结 Task、Run、Tool Call、Permission、Evidence 的 DTO 与状态图。

退出条件：空应用可启动；RPC health check、SQLite migration、UI bridge mock、单元测试和格式检查
全部可运行。

4. 每个阶段的工作卡

每项工作创建一张可审计的工程卡，至少包括：

text
目标：用户能观察到什么？
边界：涉及哪些 workspace、进程、秘密、文件和网络？
合同：新增/修改哪些 DTO、事件、migration、RPC method？
失败态：取消、重启、坏输入、权限拒绝、外部改动分别如何表现？
测试：unit / integration / desktop E2E / security / performance 哪些必需？
证据：截图、trace、日志摘要、migration fixture、发布命令输出在哪里？
回滚：如何撤销代码、数据迁移、用户可见状态和外部副作用？

没有这张卡的改动不能进入实现阶段。它让“从零重构”保持产品链路，而不是一串无关联的 crate。

5. UI 与桌面验证规则

每次影响 renderer、preload、host 或共享 DTO 的变更，在 UI 实现完成后：

  1. 先构建生产 renderer / host，再用隔离 user-data 启动真实桌面测试。
  2. 在目标桌面尺寸和一个较窄尺寸检查页面身份、非空渲染、无 overlay / console error。
  3. 走一条主交互路径，并为权限、错误或恢复至少选一条反向路径。
  4. 截图、trace 等临时 QA 产物放在仓库外；只有被明确选为设计证据的资产才进入文档包。

这条规则同时适用于 Tauri 重构版本和迁移期间的对照版本。

6. 切换与回退策略

不要把现有用户数据直接交给新版本写入。推荐四步：

  1. 并行读：新版本只读导入一个副本，验证任务、会话、工作区和附件计数。
  2. 影子运行：同一测试仓库上同时跑旧/新版本的可重复场景，比较事件、diff 和验证结果。
  3. 可选迁移：用户显式选择复制/升级数据；旧数据库保留完整备份和版本标记。
  4. 受控切换：只在发布门禁和恢复演练通过后将新版本设为默认；保留回到旧版的说明。

任何不可逆 schema 变更都要先提供导出和 dry-run，绝不把“首次启动”当作唯一恢复窗口。

7. 最终交付检查

  • 用户可以从空目录完成配置、打开项目、运行安全的只读 Agent。
  • Agent 可以经过明确审批写入、验证、审查、接受或安全回滚。
  • Terminal、外部 CLI、preview、附件、历史与证据在 Task 维度一致关联。
  • 重启、worker 退出、迁移失败、权限待决和外部修改均有可理解的恢复流程。
  • 所有产品需求编号（16）都有至少一个自动化或人工验收证据。
  • 公共合同 pin、质量门禁、许可证、签名、SBOM、更新与支持包达到 17 的发布要求。

满足这些条件后，团队可以只携带本目录和 agent-core 目录继续实现或审计 Charter；当前
仓库的实现与其它文档不再是交付前提。

本页为可离线浏览的重构规范；代码示例是实现合同，不是已交付源码。
